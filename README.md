# section-team

[![test](https://github.com/afel6/section-team/actions/workflows/test.yml/badge.svg)](https://github.com/afel6/section-team/actions/workflows/test.yml) [![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE) [![Release v0.5.1](https://img.shields.io/github/v/release/afel6/section-team)](https://github.com/afel6/section-team/releases)

## TL;DR

**What:** a Claude Code plugin that turns one session into a supervisor + specialist agents, with an Opus reviewer gate before any code is handed back.

**Install:** `/plugin install section-team --marketplace afel6/section-team` (Claude Code 2.1.275+), then start a new session.

**Cost:** about 5× normal Claude Code usage in Balanced, about 10× in Max.

**Measured result:** blind judges scored it 8.80 vs 8.16 for plain Claude Code on three unseen tasks, at about 2.2× the cost; both passed all hidden tests. See [Results](#results).

**Not for:** quick edits or questions on a tight plan — even a small change wakes a section.

A Claude Code plugin that turns every session into a **supervisor** of a small engineering team. The supervisor plans and routes; every job goes to a specialist builder **section** (frontend, backend, database, testing, security, devops, uiux, docs, ai-llm, mobile), and three advisors (ai-engineer, data-scientist, plan-advisor) give it advice without changing project files. Code goes through a **reviewer gate** before it is handed back, and work that cannot pass is handed back marked partial or ungraded. Each project picks how much the team does with one of two **modes** (Balanced or Max), or turns the team **off**; section reports are saved in the project, and a live **Team Board** shows who is working.

Current version: 0.5.1. What changed: [CHANGELOG.md](CHANGELOG.md).

## Quickstart
- **What it does:** every request goes to an Opus specialist agent (a *section*), whose code must pass an Opus reviewer before it comes back to you.
- **What it costs:** about 5× your normal Claude Code usage in Balanced (the default) and about 10× in Max, up to 13× on platform-sized tasks. Even a small change wakes a section, so it is not for quick edits or questions on a tight plan.
- **What you get:** the gain is blind-judged quality, mostly tests; hidden-test correctness ties. Judges scored the plugin's code higher than plain Claude Code's, mostly for its tests, while the hidden tests that check whether the code works never came out ahead for the plugin ([Results](#results)).
- **Install:** `/plugin install section-team --marketplace afel6/section-team`, then start a new session. A team strip appears above the prompt; ask for work as usual and the supervisor routes it.
- **Turn it off:** `/team mode off` for one project, `claude plugin disable section-team@section-team` for every project, or `claude plugin uninstall section-team@section-team` to remove it ([details](#turn-it-off-or-uninstall)).

## What changes in your sessions
- **A brief in every session.** Session start adds the supervisor's instructions to every session in every project (about 8.3K characters in Balanced, 8.9K in Max). From then on the supervisor routes work and writes no product code itself.
- **Hooks.** SessionStart, UserPromptSubmit, PreToolUse (on Write, Edit, MultiEdit, NotebookEdit, Bash, PowerShell, Agent, SubagentHandback and SendMessage), SubagentStop and Stop run in every session. They act mainly on section-team agents; the one call of the supervisor's they refuse is a SendMessage to a builder section that has finished with an oversized context. They fail open: a failure shows one line, except that the context guard and the grade check allow silently when they cannot read a transcript.
- **Files in each git repo.** `.team/notes/INDEX.md` at session start; later `.team/reports/<date>/` (every section REPORT, the supervisor's summary, and any message of 3000 characters or more, word for word), `.team/tmp/<section>/`, `.team/mode.json` once you pick a mode, and `.claude/agent-memory-local/<section>/`.
- **`.git/info/exclude`.** Two lines are added, `.team/` and `**/.claude/agent-memory-local/`, so those folders stay out of git. The plugin commits nothing to your project.
- **Your home folder.** `~/.claude/section-team/sessions/` (one status file per chat: its project folder, the first 80 characters of your latest request and its token counts; deleted after 7 days), `~/.claude/section-team/modes/` (each session's mode and brief record), `~/.claude/section-team/names.json` (only after `/team name`) and `~/.claude/section-team/office.json` (only after `/team office`).
- **A 1 s poll.** The Team Board strip re-reads the team's agents, reports and mode file every second in every session.
- **Memory guard: off** unless you set `SECTION_TEAM_MEMORY_LIMIT_MB`. When on, it stops (SIGKILL) any process the session started that holds more memory than the limit ([details](#use)).
- **Skill installs ask you.** A section may suggest a skill; the supervisor asks before installing it into `~/.claude/skills/`, unless you set `SECTION_TEAM_AUTO_INSTALL_SKILLS=1` in your user settings ([details](#sections)). A project's own `.claude/settings.json` can set environment variables too, this one included, just as it can add hooks, so check that file in repos you clone.
- **Network.** No telemetry: the hooks and the board make no network calls. Sections use WebFetch and WebSearch like any agent, and a skill search queries skills.sh and GitHub.
- **In a project set to off,** none of this happens except the strip, its poll and the chat's status file (and what a section you start there by hand saves).

## Install
In Claude Code 2.1.275 or later, one command installs it from this repo:
```
/plugin install section-team --marketplace afel6/section-team
```
On older versions, run `/plugin marketplace add afel6/section-team`, then `/plugin install section-team@section-team`.

### Turn it off or uninstall
- **One project:** `/team mode off`, or the **Off** entry in the strip's Mode picker; `/team mode balanced` turns it back on. It applies from your next session ([Modes](#modes)).
- **Every project, still installed:** `claude plugin disable section-team@section-team` (or `/plugin`, then disable section-team); `claude plugin enable section-team@section-team` turns it back on.
- **Remove it:** `claude plugin uninstall section-team@section-team`.
- **What stays behind** (delete it by hand if you want): `.team/` and `.claude/agent-memory-local/` in each project, the two lines in each repo's `.git/info/exclude`, `~/.claude/section-team/`, and any skill you installed into `~/.claude/skills/`.
- **Emergency:** `claude --safe-mode` starts Claude Code with plugins off.
- The disable and uninstall commands are the ones `claude plugin --help` lists on Claude Code 2.1.318; a fresh-profile run of the marketplace install, disable and uninstall has not been recorded yet.

### From a clone (to work on the plugin)
```bash
git clone https://github.com/afel6/section-team.git
```
- Try it once: `claude --plugin-dir <path-to-section-team>`.
- Keep it on: in `~/.claude/settings.json`, set `env.CLAUDE_CODE_PLUGIN_DIRS` to the clone's path. New sessions pick it up.
- Off: set `"section-team@inline": false` under `enabledPlugins`, or remove the env entry.

The section agents are generated: edit the roster in `scripts/gen-agents.mjs` and run `node scripts/gen-agents.mjs`. Skills you give a section with `node scripts/assign-skill.mjs <skill> <section>...` are kept in `scripts/roster-extra.json`.

## Results
Every gain measured so far is in blind-judged quality, mostly tests. Hidden tests, which check whether the code works, show no gain: they tied in most rounds, the plugin passed fewer than plain Claude Code in the first three p1 rounds (Max 210 of 264 in the 0.2.3 round, where one Max run timed out, and 261 to 263 otherwise, against 264), and Max passed 2 more of 148 on one hq task (2 runs). Each result rests on 2 or 3 runs per setup, on Node.js tasks with no npm packages, run headless with any plan approved in advance.

**Pre-registered rounds** (public freeze tag, targets set before the round, raw data published). Both measured older versions than the one you install:

| Round | Version measured | Tasks | Judge quality, plugin vs plain Claude Code | Hidden tests | Cost × plain | Raw data |
|---|---|---|---|---|---|---|
| Held-out, 2026-10-31 | v0.1.1, where the supervisor still built small and single-area work itself | 3 new tasks, 3 runs | 8.80 vs 8.16 (Opus judges) | all passed by both | about 2.2× | [`bench/data/heldout/`](bench/data/heldout/) |
| Mode round, 2026-11-04 | v0.2.1 (Lean, Balanced and Max; 0.3.0 removed Lean and rebuilt Max) | 3 new tasks, 3 runs, clean machine | Balanced 8.77 and Max 9.06 vs 7.37 (Opus); the outside Codex judge saw about half the gap | all passed by every setup | Balanced 5.24×, Max 9.66× | [`bench/data/modes/`](bench/data/modes/) |

**Rounds on the rules that ship (0.3.0 and later).** Their targets were set before each round but recorded privately, so they are not publicly pre-registered:
- **The p1 rounds (2026-11-07 to 2026-11-18)** built one help-desk platform in three stages, judged by Codex and later Fable too. The sections' rules were tuned on this task, so these results are in-sample. Balanced judged 1.0 to 1.75 above plain Claude Code on Codex at 3.4 to 6.0× the cost; Max cost 8.4 to 13.0×. Raw data for ten of these rounds is in [`bench/data/p1/`](bench/data/p1/); rounds py and ph are reported, raw data not published.
- **Round hq (2026-11-19, plugin d795636: 0.3.0 plus the p1 fixes)** ran three other tasks. Balanced scored 8.58 (Codex) and 8.50 (Fable) against 7.92 and 7.17 for plain Claude Code at 5.2× the cost, missing both of its pre-set bars; Max scored 9.42 and 9.00 at 10.5× and ranked first in all 12 cases on both judges. Reported, raw data not published. Its two-stage task h7 shares a requirement word for word with p1.
- **Round fx (2026-11-20)** checked one Balanced fix, which missed its bar and does not ship. Reported, raw data not published.
- **Round 17 (in-sample tuning, v0.1.x):** judge quality 8.6 against 7.1, at $3.10 against $0.85 per task. Its "plugin off" baseline was the author's own setup, with their CLAUDE.md and other plugins on.

Every round's numbers, targets and judge findings: [docs/benchmark-p1-hq-fx-2026-11.md](docs/benchmark-p1-hq-fx-2026-11.md); the first 17 rounds: [docs/benchmark-2026-10-24.md](docs/benchmark-2026-10-24.md). Never benchmarked: the database, devops, uiux and mobile sections, the data-scientist advisor, any non-Node stack, and the desktop flows. Not measured: any saving in real use.

## Requirements
- Claude Code with plugin support. The Team Board strip, `/team` and `/chats` use the Mods API (`hooks/register.tsx`), an early-access Claude Code API that may change between releases; the board tests run on Claude Code 2.1.318.
- Access to the Claude 5 models: sections and the reviewer run on Opus 5.5, the coder helper on Sonnet 5.5, the scout helper on Haiku 5.5.
- Node.js 22.3 or later (or 20.16 or later) on your PATH for the hooks and tests, because they use `process.getBuiltinModule`, and git 2.31 or later. CI runs `npm test`, the agent-file check and the bench tests on Linux, macOS and Windows with Node 26, and `npm test` on Node 20.16 and 22.3. The Team Board tests (`npm run test:board`) and plugin validation (`npm run validate`) need the Claude Code CLI and run only locally.
- For headless runs (`claude -p`), set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`. Otherwise `claude -p` stops background subagents 10 minutes after the last turn, which cut off the testing section's final review in a probe on Claude Code 2.1.296. The mode round ran this way, with a time limit on each run.
- Recommended skills, preloaded by some sections: `frontend-design` (frontend), `tdd-workflow` (testing), `claude-api` (ai-engineer; ai-llm loads it when the job calls Claude), `web-design-guidelines` (uiux). Sections load `security-review` only when the branch shares history with an `origin/HEAD` ref (`git merge-base HEAD origin/HEAD` succeeds), because the skill runs `git diff origin/HEAD...` as it loads. Other skills a job names are loaded only if they are installed.

## Use
- Just talk to the supervisor. Every job goes to a builder section, so the supervisor's chat stays small. In Balanced mode (the default): a small task (about 50 lines, one or two small functions) or a single-area task (up to about 600 lines) wakes the matching builder section, which writes the code, its tests and any README asked for, and runs its own reviewer gate; a feature with its own behaviour to test (a CLI, an endpoint, a module with storage or I/O) is never small. Multi-area work wakes the builder sections plus testing. 3+ builder sections (testing, docs, the security pass and advisors not counted) → it shows a plan first. Max changes these steps; see [Modes](#modes).
- Sections message each other directly by agent id and share contracts as notes in `.team/notes/`. If an id is missing or a message fails, the supervisor forwards the request with the asker's id, so the owner replies to the asker directly.
- The supervisor names up to 4 skills per job (`Skills for this job:`), picked from what is installed and fits that section and task.
- Reports: `.team/reports/<date>/` in each project. Every REPORT has a `Status:` line (`done`, `partial`, `blocked` or `ungraded`) and a `Quality:` line, the reviewer's grade (see Sections) or `n/a (no code)`. `ungraded` means the section truly could not run its reviewer gate (for example, it had no Agent tool) and says why; the supervisor then runs `section-team:reviewer` on that work with the mode's gate. Each saved file ends with a `Plugin:` line naming the plugin version and the project's mode. The plugin also saves the supervisor's summary (a last message with the line `## Team summary`) as `<time>-supervisor-summary.md` (Stop hook).
- Notes: `.team/notes/` in each project, `INDEX.md` plus one file per note. Notes and reports both live under `.team/`, kept out of git via `.git/info/exclude`; to keep them in git, create `.team/keep-in-git` and delete the `.team/` line from `.git/info/exclude`. The plugin makes `.team/tmp/<section id>/` for a builder's scratch files; the empty folder stays, inside the git-ignored `.team/`.
- Long messages and hand-backs: a pasted message of 3000 characters or more is saved word for word to `.team/reports/<date>/<time>-user-request.md` inside a git repo whose `.team/` folder git ignores, so the supervisor points sections to it instead of re-typing it. Sections put long output (probe logs, spec readings, flow output) in a `-details.md` file there and keep at most 5 short lines above their REPORT; a builder hand-back that claims done with more than 1200 characters above its REPORT is refused (partial, blocked and ungraded are not; PreToolUse hook). A resumed session gets the brief again only when it changed since the session started. In the p1 measure round the supervisor's chat peaked at 99K to 104K in Balanced and 116K to 123K in Max, against 158K to 168K for solo.
- **Memory guard (opt-in).** It is off by default on every platform. To turn it on, set `SECTION_TEAM_MEMORY_LIMIT_MB` to a whole number of MB (for example `12288` on a 16 GB machine) under `env` in `~/.claude/settings.json`; `0` or a value that is not a whole number keeps it off. Once on, the first Bash or PowerShell call by a section in a session starts one guard in the background. It checks every 5 seconds and stops (SIGKILL) any process the session started that holds more memory than the limit: sections' commands, the supervisor's own commands and the session's MCP servers alike (never Claude Code itself). Each stop is logged with its command line in `.team/tmp/memory-guard.log` in the project.
- If a plugin hook fails, or has to skip its job (for example, its input names no project folder), you see one `section-team` line saying so, instead of silence. The exception: the context guard and the grade check allow silently when they cannot read a transcript.

## Modes
Each project runs in one of two modes. Lean, the third, was removed in 0.3.0: a project that saved it runs as Balanced, with a line at session start saying so, until you pick a mode. Balanced is the default; 0.2.3 changed it with the security wake-up, docs last and the whole-stack final review. The picker's labels round the usage measured in the [mode round](docs/benchmark-modes-2026-11.md) and round hq of 2026-11; platform-sized tasks cost more, as below. "Measured" compares each mode with Claude Code with every plugin off, on a clean machine with no user instructions, over three new tasks: quality is blind Opus judge quality out of 10 (plain Claude Code: 7.37), and usage is cost over all three tasks, then on the two single-area tasks alone. Every setup passed every hidden test, and the setup with more test lines won almost every comparison, so read the quality gaps with that in mind. On the platform-sized task p1 usage ran higher: in rounds tg to ph Balanced cost 3.4 to 6.0 times and Max 8.4 to 13.0 times plain Claude Code (see [the round details](docs/benchmark-p1-hq-fx-2026-11.md)). On round hq's two-stage platform task (h7), Balanced cost 6.6 times and Max 12.8 times plain Claude Code, and Max was ranked first in every judged case on both judges, so for platform-sized work Max is the stronger pick.

| Picker label | Measured on v0.2.1 (mode round, 2026-11; Max was rebuilt in 0.3.0) | What changes | Reviewer gate |
|---|---|---|---|
| Balanced · ~5× usage | Quality 8.77, +1.40 over plain Claude Code (bar met, Codex confirms). Usage 5.24×, then 4.26×. | The steps under [Use](#use). | Opus reviewer. Pass: overall at least 8 and no item under 6. 2 fix rounds. |
| Max · ~10× usage | Quality 9.06, +0.29 over Balanced (bar not measurable: Balanced is above the 8.60 scale ceiling; Codex does not confirm). Usage 9.66×, then 7.52×. | Balanced's flow plus proof steps. A single-area task with new concurrent writes, protocol framing, auth or crypto, on a product with no foundation note, first gets a short design note that `plan-advisor` checks before any code. A builder's own tests are written before its code (in Balanced after it; in both from the spec, not from the code). The testing section probes even small tasks. Single-area code that takes user input or touches files or the network also gets a security review. Multi-area work gets a security pass, then two final reviews by two fresh testing sections (the second is not shown the first's REPORT; it reads the code against the spec instead of probing again), and always wakes docs. Before it says done, the supervisor runs the testing section's one command that prints a PASS or FAIL line per critical flow. Every hand-back with a changed file, docs and config included, needs a reviewer grade. | Opus reviewer. Pass: overall at least 9 and no item under 7. 2 fix rounds.

- **Pick a mode:** the **Mode** picker on the team strip, or `/team mode balanced|max|off`. `/team mode` alone shows the current mode and the choices; `/team` alone still opens the board. An unknown mode is refused and nothing is saved. On mobile the strip has no picker: tap its mode button to see the command.
- **Turn it off in one project:** `/team mode off`, the **Off** entry in the Mode picker, or `{"mode": "off"}` in the project's `.team/mode.json`. Sessions in that project then get no brief: the supervisor is plain Claude Code, session start writes nothing (no `.team/` folder, no `.git/info/exclude` edit, no session records), and prompts are not saved or checked. A section you start by hand there still saves its REPORT and makes its `.team/tmp/` folder, and a message headed `## Team summary` is still saved. The strip still shows, so you can turn it back on with `/team mode balanced`. Turning it off, or back on from off, applies from your next session. A committed `{"mode": "off"}` turns the team off for everyone who clones the repo.
- **When it applies:** a new session starts in the project's mode. A change mid-session applies from your next message: the supervisor is told the new mode and its rules, and the handback gate uses the new mode's pass mark at once. A change to `autoInstallSkills` applies from the next session.
- **Mode file:** the choice is saved in `.team/mode.json` at the project root (the main checkout of a git repo, so its worktrees share it; else the session's folder), for example `{"mode": "max"}`. It may also hold `"autoInstallSkills": false`, which turns automatic skill installs off for that project; a `true` there is ignored with a one-line notice, because a cloned repo can commit this file, so only the `SECTION_TEAM_AUTO_INSTALL_SKILLS=1` environment variable turns them on (set it in your user settings; a project's own `.claude/settings.json` can set it too, so check that file in repos you clone). Both keys are optional. No file means Balanced. A session that starts with a broken file (bad JSON or an unknown mode; a saved `lean` is not broken, it runs as Balanced) runs Balanced, and a one-line message says what was wrong. If the file breaks mid-session, the session keeps its mode (the supervisor and the handback gate both), and each prompt shows a one-line warning until the file is fixed; a `/compact` or `/clear` while it is broken starts the session over in Balanced. Like the rest of `.team/`, it stays out of git by default, but a repo can still commit one.

## Team Board
- Nothing opens by itself. A one-line team strip above the prompt shows who is awake, the team's tokens and helpers, how many sections sleep and the project's mode (the **Mode** picker); its **Board** button opens the board.
- `/team` opens the Team Board. Each awake section has a box with its live token use, how many helpers it started by model, and its reviewer grade once it is done; a section that ends `partial`, `blocked` or `ungraded` shows as a problem. Sections nobody woke are folded into one "N asleep" line in the terminal. On desktop, VS Code and mobile that line is replaced by the office (below). The office has board tests for the desktop and mobile surfaces; it has not yet been tried by hand on VS Code or mobile, and the final build has not been looked at on a live desktop board.
- **The office:** on desktop, VS Code and mobile the board shows an office picture with ten desks, one per builder section, each with a prop, a chair and a nameplate with the creature's name. The default names are frontend Iris, backend Moss, database Atlas, testing Pico, security Ward, devops Rigg, uiux Lumi, docs Page, ai-llm Echo and mobile Zip. A creature sits at its desk while its section has work (running, waiting or a problem). While its section is free it strolls the corridor between the rows; a sleeping creature strolls too, with an idle face, and a creature whose section is done walks back to the corridor happy and keeps its sparkle. A creature walks to its desk when work starts and back when it ends. The three advisors (ai-engineer, data-scientist, plan-advisor) have no desk. Builder card headers show `● <name> · <id>`.
- **Names:** `/team name <section> <name>` renames a builder, `/team name <section>` gives back its default name, and `/team name` lists all ten. A name is 1 to 12 letters (any alphabet, accents included), digits, spaces or dashes, and starts with a letter or digit. Each default name is kept for its own builder, and two builders cannot share a name. Names are saved per user in `~/.claude/section-team/names.json`, so they follow you to every project. The strip, `/chats` and the status files keep section ids.
- **Office look and fling:** `/team office yellow` paints the office yellow (butter walls, a honey floor, a sunny sky and a caramel rug), `/team office night` brings back the dark office, and `/team office` says which one you have. The look is saved per user in `~/.claude/section-team/office.json`, like the names. On desktop and mobile, press and hold a creature to squish it, and click it to fling it: it flies, spins, bounces and comes back to its spot. VS Code draws the office as a still picture, so there is no fling there. The fling has board tests and was checked by hand in a Chromium browser; it has not yet been tried in the desktop app.
- The terminal keeps the text board. It shows the cards and the strip as before, with the names in the card headers.
- `/chats` opens a dashboard with one card per open chat: needs you, working or idle (a chat quiet for 30 minutes is idle; one that ended or has been quiet for a day drops off). It reads one status file per session in `~/.claude/section-team/sessions/`. A status file holds the project folder, the first line of your latest request (cut to 80 characters), the awake sections and the token and helper counts. Status files older than 7 days are deleted at session start.

## Sections
Builders: frontend, backend, database, testing, security, devops, uiux, docs, ai-llm, mobile. Advisors (they advise and change no project files; a hook limits their writes to their own memory folder): ai-engineer, data-scientist, plan-advisor.
Section heads work like solo builders. Each reads `.team/notes/INDEX.md` first, plans its part, then hands independent tasks out in parallel to cheap helpers (not sections, not on the board as cards): `section-team:scout` (Haiku, read-only: reads and searches, returns file:line facts) and `section-team:coder` (Sonnet, routine code and tests from the head's spec). Both helpers can load skills with the Skill tool. Heads run helpers in the foreground (`run_in_background: false`; several in one message still run in parallel), because a head that waits on a background helper ends its turn and is made to hand back unfinished. The plugin refuses a section's Agent call that asks for the background (PreToolUse hook). Where the Agent tool has no such option (the desktop app), helpers run in the background and the head keeps working until their results are in. The head keeps design, tricky bugs and integration for itself. Advisors may use the scout but not the coder.
- **Notes:** a head writes a note in `.team/notes/` for anything other sections depend on (an API, a schema, design tokens, a file layout) and adds one line to `INDEX.md` (`<file> — <owner section> — <one-line summary> — <date>`). Only the owner edits its note; shared decisions are appended to `.team/notes/decisions.md`.
- **Skills:** each section preloads at most one core skill; every other skill loads on demand, the job's `Skills for this job:` list first. If no installed skill fits, a section searches the open directory read-only (`skills.sh/api/search`) and names a `Suggested skill:` in its REPORT; it never installs. The supervisor lists the suggestion in its summary and asks you; on yes it installs it through `section-team:add-skill` (a safety review, then the install) for that section. To let it install without asking whenever the review finds no red flag, set `env.SECTION_TEAM_AUTO_INSTALL_SKILLS` to `1` in `~/.claude/settings.json` (a project's [mode file](#modes) can turn this off, never on); a red flag, or an existing skill of the same name, still stops the install and you are told. When a job needs a skill nobody has, the supervisor searches skills.sh and GitHub through `section-team:add-skill`: it asks you before installing what it found, unless `SECTION_TEAM_AUTO_INSTALL_SKILLS` is `1` and the skill's GitHub owner is one you listed in `skills/add-skill/trusted-sources.json`, which ships empty.
- **Clean-code gate:** once the helpers' code is in, a builder sends its changed files to `section-team:reviewer` (never edits). In Balanced, the default: Opus grades, the pass is overall at least 8 out of 10 and no item under 6, and there are at most 2 fix rounds; the project's [mode](#modes) sets these numbers. On a fail the fix list goes to a coder and the reviewer grades again; if it still fails the section ends `Status: partial` with the grade. In Max, a REPORT whose Changed line names any file, docs and config included, needs a grade too. Jobs that change no code skip the gate in Balanced; a config file on the Changed line counts as code. The plugin checks it at handback, best effort: a builder whose REPORT lists changed code but no grade, says done under the mode's pass mark, or says done while its reviewer scored an item under the mode's item minimum, cannot hand it back (PreToolUse hook on `SubagentHandback`). It must run the reviewer first, or hand back honestly as `Status: partial`, `blocked` or `ungraded`. The check reads the section's own REPORT text (a Changed line that names no file counts as no code) and fails open: when it cannot read a transcript or hits an error, the hand-back goes through.
- **Memory:** each section keeps its memory per project, one folder per section in `.claude/agent-memory-local/` under the session's folder (in a git worktree session, the worktree's folder). At session start section-team adds `**/.claude/agent-memory-local/` to the repo's `.git/info/exclude`, even with `.team/keep-in-git`, so memory folders stay out of git in every folder of the repo. Remote sessions (`CLAUDE_CODE_REMOTE_MEMORY_DIR`) keep memory elsewhere, so advisors there cannot save memory. Before 0.2.0 one memory served every project; those notes stay in `~/.claude/agent-memory/section-team-*`, and copying one of those folders into a project's `.claude/agent-memory-local/` brings it into that project. Advisors may write only inside their own memory folder there.

- **Tools and MCP grants:** builder heads get Read, Write, Edit, Grep, Glob, Bash, PowerShell, Skill, Agent, SendMessage, ToolSearch, Monitor, TaskStop, WebFetch and WebSearch, and no project MCP servers. frontend, testing, uiux and ai-llm also list three browser MCP servers: `mcp__Claude_Browser__*` (the desktop app's built-in browser, separate from your Chrome but keeping any sign-in you made in it), `mcp__chrome-devtools__*` and `mcp__playwright__*` (which browser profile those use depends on how you set those servers up). Whether these wildcards take effect has not been checked live. No section gets `mcp__claude-in-chrome__*`, which drives your own logged-in Chrome. Advisors get Read, Grep, Glob, WebSearch, WebFetch, Skill, SendMessage, Agent, Write and Edit, and a hook allows their writes only inside their own memory folder (best effort: it allows the call if it crashes).

Section heads skip your global `CLAUDE.md` (it can cost many thousands of tokens per agent) but read the project's own rule files (`CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.claude/rules/*.md`), and carry a short copy of the house rules.

## Platform readiness (0.2.3)
Changes aimed at long sessions and real multi-area platforms:
- **Fresh sections for new jobs.** A section that is kept alive across many jobs re-reads its whole history on every turn, which gets expensive. In 0.2.3 the supervisor is told to start a fresh Agent call for each new job; a message to a section only continues that same job (a fix list, a question, a resume). Builder heads also get a shorter tool list, and are told to keep tool output short. The cost of the shorter list is that builder heads have no project MCP servers: they use a CLI, or ask the supervisor to make the call. A limited head still gets `SubagentHandback`. Those sizes are one PC's measurement, taken on 2026-11-05 (Claude Code 2.1.318, about 40 plugins and 629 skills, a throwaway probe of copies of a real head told to reply "ok", not a benchmark). In the desktop app, where the difference is large, the default head starts at 71.8K tokens and a limited-tool helper at 24.7K; a limited section head has not been measured there. In the terminal the same head starts at 40.0K by default and 32.9K with the branch's tool list. The skill list alone is 30K characters on that PC; it depends on what you have installed, not on the plugin.
- **Context guard.** The guard refuses only a section that has finished: a message to a builder section that has finished with its context over 300,000 tokens is refused. A section or helper whose message is refused is sent to the supervisor (`main`), which starts a fresh section; the supervisor itself is told to start a fresh one pointed at the notes, its REPORT if it left one, and its changed files. A section still working takes messages at any size. If the plugin cannot read the needed files, it allows the message.
- **Grade check.** Only a builder REPORT that claims done with code is checked; `partial`, `blocked` and `ungraded` are not. Its grade is now compared with the reviewer's own grade in its transcript. A grade above the reviewer's, or a grade with no reviewer call, is refused at handback. If the result cannot be read, nothing is refused.
- **Foundation skill.** `section-team:foundation` is loaded by the supervisor before a new platform or product with two or more builder areas; other work with 3 or more builders keeps the short plan. It asks the user at most 5 questions, writes a short `.team/notes/foundation.md` (stack, data model, contracts, build order as vertical slices, test plan), waits for your OK, then builds one slice at a time, or slices that share nothing side by side, with a whole-stack check after each. `.team/notes/plan.md` tracks the slices so a new chat can carry on.
- **Max single-area foundation (after 0.3.0).** In Max, a single-area task with new concurrent writes, protocol framing, auth or crypto also loads it, for that one area, on a product with no foundation note: a short note checked by `plan-advisor` and frozen, with no questions, no OK and no slices.
- **node:http skill (after 0.3.0).** The backend section loads `section-team:node-http` only for a server built on node:http itself, with no web framework; it holds the rules for the replies Node writes itself, requests sent in one write, request bodies and a client that ends its sending side first.
- **Brief rules.** In Balanced, multi-area work touching auth, payments, uploads or secrets also wakes the security section; Max's security pass is unchanged, see [Modes](#modes). In every mode the docs section comes after the builders report, and the final review starts the app and drives the critical flows.
- **A two-stage benchmark task.** `bench/tasks/h7.md` is a two-stage task (build, then change it) with hidden tests for each stage and for stage-1 behaviour surviving. It exists to show whether the code is really better, because earlier tasks were passed by every setup.

**What is measured and what is not.** The cost figures behind these changes come from `bench/transcript-cost.mjs`, which prices a one-off replay of private local transcripts from 2026-10-24 to 2026-11-04 with the rates in that file: a rough model, not a bill. The replay itself is not in this repo; tests, commit messages and the platform-readiness plan (its Evidence table holds the main ones) quote some of its figures. The Modes figures and the Results figures above the p1 rounds were measured before 0.2.3. The p1 rounds ran the brief rules live, and from 0.3.0 on the foundation skill too: `plan-advisor` checked the stage-2 note in every judged round's team runs, and in round ph Max's one-area note at stage 1. The guard, the limited heads, the grade check and the two-stage harness have only unit tests until a live check confirms them. Not measured yet: any saving in real use, and any gain in code quality or in hidden-test failures. Round hq has since run h7, but on one plugin version, comparing the modes with plain Claude Code rather than the plugin before and after 0.2.3, so treat 0.2.3's changes as unproven until such a check runs.
