# section-team — review brief for an external grader

Repo: `<path-to-section-team>` (branch `feat/claude-team`, 26 commits on top of `main`). Platform: Claude Code 2.1.295/2.1.296, Claude desktop app (Code tab) and CLI, native Windows 11, Node 26.

## 1. What it is

A personal Claude Code **plugin** (`section-team`) that changes how every Claude Code session works:

- Every session becomes a **supervisor**. The user talks only to it.
- The supervisor does small jobs itself. For real work it wakes **specialist "section" agents**, one per coding area. Each section has its **own context window**, its own long-term memory, and can call its own helper agents on cheaper or stronger models.
- Every section ends with a structured **REPORT**. The REPORT goes to the supervisor and is saved in the project (`.team/reports/`).
- A live **Team Board** pane shows the supervisor and every section's state, its live token use, and how many helpers it started and on which models.
- An **add-skill** helper installs a skill from a GitHub URL after a safety review, and assigns it to the right sections.

It is loaded globally through `env.CLAUDE_CODE_PLUGIN_DIRS` in `~/.claude/settings.json`, so it applies to every new session in every project.

## 2. User requirements it was built against

1. A main view with one big supervisor box and one box per specialty.
2. Each specialist works like a fresh session: own context, can call subagents.
3. Specialists ("sections") communicate.
4. The user talks only to the supervisor.
5. The supervisor uses all skills and tells each section which skills to use.
6. Every agent reports, to the supervisor and as saved files.
7. Global: works in every project, for this one user.
8. Section heads run on Opus 5.5 and choose models (Haiku/Sonnet/Opus/Fable) for their helpers.
9. Two read-only advisors (AI engineer, data scientist) advise the supervisor.

Full spec: `docs/specs/2026-10-12-claude-team-design.md` (v4). Implementation plan: `docs/plans/2026-10-12-claude-team-plan.md`.

## 3. Architecture

```
You ──► SUPERVISOR (your normal session; brief injected by SessionStart hook)
          ├─ small task → does it itself
          ├─ AI/data decision → asks an advisor (read-only) first
          ├─ 3+ builder sections → shows a plan, waits for OK
          └─ wakes sections: Agent(subagent_type "section-team:<id>") → keeps id ↔ agentId map
                section head (Opus 5.5, own context, own memory folder)
                  ├─ helpers on haiku / sonnet / opus / fable (explicit per call)
                  └─ needs another section → SendMessage main → supervisor relays
                ends with ## REPORT ──► supervisor (completion notification)
                                   ├─► SubagentStop hook → .team/reports/<date>/<HHMMSS>-<id>.md
                                   └─► Team Board box
You ◄── combined summary (also saved)
```

| Part | Files | Runtime | Job |
|---|---|---|---|
| Supervisor brief | `brief/supervisor.md`, `hooks/session-start.mjs` | classic SessionStart hook (Node) | Injects the rules on startup, resume, /clear and compact; adds `.team/` to `.git/info/exclude`; names the last summary |
| 12 sections | `agents/*.md`, generated by `scripts/gen-agents.mjs` from one roster | Claude Code subagents | 10 builders (frontend, backend, database, testing, security, devops, uiux, docs, ai-llm, mobile) and 2 advisors (ai-engineer, data-scientist) |
| Report saver | `hooks/subagent-stop.mjs`, `hooks/lib/report.mjs`, `hooks/lib/paths.mjs` | classic SubagentStop hook | Reads the section's final handback from its transcript, extracts `## REPORT`, saves it without ever overwriting |
| Advisor guard | `hooks/pre-tool-use.mjs` | classic PreToolUse hook | Advisors: no shell, Write/Edit only in their own memory folder, only read-only helper types |
| Team Board | `hooks/register.tsx`, `hooks/board-model.mjs`, `types/index.d.ts` | mods runtime (TSX, `$` API) | Pane opens at session start; polls `$.agent.list()` and today's reports every second; per-section token totals from `turn.step` usage (streaming hook, pass-through) and helper models from `agent.spawn` (`parentAgentId` roll-up); resets on `/clear`; `/team` reopens it |
| add-skill | `skills/add-skill/SKILL.md`, `scripts/assign-skill.mjs`, `scripts/roster-extra.json` | plugin skill and Node CLI | URL validation → fetch to temp → full safety review → user OK → install → assign to sections → regenerate agents → commit |

## 4. Platform facts that shaped the design (measured in a Phase 0 spike, `docs/phase0-results.md`)

- The Agent tool has **no `name` parameter** in this build. Sections are addressed by the agentId their spawn returned.
- Sections **cannot message each other** (no names; sibling ids unknown). Cross-section requests are **relayed by the supervisor**.
- SubagentStop carries **no `last_assistant_message`**. The final text is the last `SubagentHandback` tool_use in the transcript.
- Plugin agent types are namespaced `section-team:<id>`. Memory folders are `~/.claude/agent-memory/section-team-<id>`.
- Agent teams (true peer sessions) exist but are experimental and CLI-only (not in the desktop app), so they were deliberately not used.
- Plugin names may not start with `claude-`, hence `section-team`.

## 5. Key design decisions (and why)

| Decision | Why | Cost |
|---|---|---|
| Subagents and a mod instead of agent teams | Works in the desktop app; stable features | No direct peer chat (relay hop instead) |
| One generated roster for 12 agent files | Shared rules cannot drift | Must run the generator after edits (guarded by a `--check` test) |
| Logic in plain Node hooks, UI in the mod | Node: full fs and plain `node:test`; mods API is early access | Two runtimes |
| Plan-first at 3+ builders | Protects usage and lets the user steer | One extra round-trip on big tasks |
| Testing section owns final review | Avoids every section re-reviewing the same diff | Testing section is a bottleneck |
| Advisors read-only, enforced by a hook | The prompt alone was leaky (Explore/Plan helpers carry Bash) | One Node process per write/shell/agent call (~150 ms) |
| Reports out of git by default (`.git/info/exclude`) | No noise in the user's repos | Opt-in via `.team/keep-in-git` |
| Board auto-opens (user decision) | Visible team state | 1-second poll in every session |

## 6. Quality evidence

- **Tests:** `npm test` gives 97/97 (node:test: report parsing, paths and worktrees, hooks end to end with Windows paths containing spaces, Arabic UTF-8, malformed stdin, the guard including junction launch, the generator, and assign-skill including a temp-copy CLI end to end). `npm run test:board` gives 17/17 (`claude plugin test`: pane render on terminal and desktop surfaces, poll lifecycle, retry after a failed write, auto-open, live usage and helper-model lines driven through real `agent.spawn`/`turn.step` hooks, reset on `/clear`). `claude plugin validate --strict .` is clean.
- **Process:** each task had TDD (RED then GREEN recorded), an independent spec+quality review, and fix rounds until clean. Then a whole-branch review on Opus (5 Important findings fixed, re-reviewed), and a 3-round security review of add-skill (shell injection via URL parts, prompt injection via fetched skill text, load-time command execution).
- **Acceptance (CLI, `docs/acceptance-2026-10-12.md`):** a real 3-section build (backend + frontend + testing) produced per-section REPORT files and a summary, `.team/` was git-excluded, the built project's own tests passed 16/16, and `-p` exited promptly. Advisor guard: verified directly. Live, the advisor refused on its own, so the hook's deny was not exercised in a live run.
- **Acceptance (desktop):** confirmed that the plugin loads, the supervisor brief is active, all 12 agents are listed, and the board auto-opens with the right layout. **Not yet run live:** the full desktop build test, relay via `main` (row 9), reuse capture (row 10), the Fable consent prompt, and supervisor identity after `/clear`.

## 7. Known limitations (honest)

- **Relay mechanism not yet observed live.** In `-p`, the supervisor passed the API contract between sections itself; no section sent `SendMessage main`.
- **Reuse capture** (a section resumed for a second job saves the second report) is covered by unit tests on realistic transcript shapes, not by a live run.
- **Status parsing** is heuristic (the `done|partial|blocked` regex has no word boundaries).
- **Per-call overhead:** each Write/Edit/Bash/Agent call in any session spawns Node for the guard (~150 ms). The board polls once a second in every session, and a pass-through hook runs on every model step to count tokens.
- **Usage numbers** are counted inside the session from model-step usage; they are not reconciled with the account's billing view, and the counting maps are not pruned during very long sessions.
- **Agent-id map lost** after `/clear` or compaction: the supervisor respawns sections and their in-session context is lost (long-term memory survives).
- **Model cost:** all 12 heads are pinned to Opus 5.5 (user choice).
- Deferred minor items and every controller ruling are listed in `docs/build-ledger.md` (lines marked `minor (deferred)` and `Ruling`).

## 8. Expected outcomes vs a single session (author's assessment, unmeasured)

- **Tokens:** expected to cost **more** in total for multi-area work, not less. Each woken section is a fresh Opus context that re-reads the code and reloads the user's large global instructions; job messages, reports and relays add overhead. Rough expectation: 1.5–4× a single session for the same multi-area task. It saves tokens only in specific places:
  - the supervisor's own context stays small (only REPORTs come back), so long sessions hit compaction less;
  - small tasks skip the team entirely;
  - routine helper work runs on Haiku/Sonnet.
- **Quality:** expected to be **better for medium-to-large, multi-area work**: focused contexts, specialist prompts, parallel independent parts, a dedicated testing/review gate, saved reports, and per-area memory. Expected to be **equal or worse for small or tightly coupled changes**: handoff loss, sections rediscovering the code, relay latency, and integration seams between sections.
- **How to measure:** run the same 3 tasks (one small fix, one single-area feature, one multi-area feature) once with the plugin on and once off (`"section-team@inline": false`). Compare usage, wall time, tests passing and review findings.

## 9. Suggested grading rubric

| Dimension | What to check | Where |
|---|---|---|
| Requirement fit | Each item in §2 has a mechanism; deviations are justified (relay instead of peer chat) | spec §1–§3, `brief/supervisor.md`, `agents/*.md` |
| Correctness | Hooks never break a session (exit 0, no stdout on bad input); reports never overwrite; worktree-safe paths | `hooks/*.mjs`, `tests/*` |
| Security | Advisor guard bypasses; add-skill URL/path validation; prompt injection from fetched skills; nothing executes at skill load | `hooks/pre-tool-use.mjs`, `skills/add-skill/SKILL.md` |
| Robustness | Windows paths with spaces, CRLF, UTF-8, missing git, symlink/junction launch, `/clear` | tests, `hooks/lib/paths.mjs` |
| Code quality | Small focused files, pure helpers, immutability, generated roster with drift check | `hooks/lib`, `scripts` |
| Tests | Real behaviour (spawned hook processes, temp git repos and worktrees), not mocks | `tests/` |
| Cost/efficiency | Per-session overhead (Node per tool call, 1 s poll), token impact of 12 Opus heads | §5, §7, §8 |
| Usability | Board clarity, plan-first gate, README accuracy, on/off switch | `README.md`, board screenshots |
