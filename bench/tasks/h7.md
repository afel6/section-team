Build a parts-store app: an HTTP server `server.mjs` (an ES module, run as `node server.mjs`) that serves a JSON API and a browser page, and keeps all its data in one SQLite database file through `node:sqlite`.

Server
- At startup the server checks `PORT`, then opens the database, then starts listening, in that order.
- It listens on 127.0.0.1 at the port in the `PORT` environment variable. An unset or empty `PORT` means 3000. A `PORT` that is not made only of ASCII digits 0-9, or whose value is above 65535, or a port that cannot be bound, makes the server write one line of its choice to stderr and exit with code 1.
- Once listening, it prints `listening on http://127.0.0.1:<port>` followed by "\n" to stdout, where `<port>` is the port actually bound (with `PORT=0`, the port the OS picked). This line is the only thing the server ever writes to stdout.
- The database is the file named by the `DB_FILE` environment variable. An unset or empty `DB_FILE` means `parts.db`. A relative `DB_FILE`, the default included, is resolved against the current working directory.
- A file that does not exist, or is empty, or is a database with no tables and `user_version` 0, gets the schema below. A database with `user_version` 1 is used as it is. Anything else (the file or a folder on its path cannot be opened or created, the file is not a SQLite database, or it is a database with any other `user_version`, or with `user_version` 0 and tables in it) makes the server write `cannot open database <name>` followed by "\n" to stderr, where `<name>` is the value of `DB_FILE` as given (`parts.db` when it is unset or empty), and exit with code 1 without listening and without changing the file.

Schema
These tables are a contract: other tools read and write this file. Create exactly these tables and columns, with no other tables, columns or triggers (indexes of your own are fine).

```sql
CREATE TABLE parts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  sku TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL
) STRICT;
CREATE TABLE moves (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  part_id INTEGER NOT NULL REFERENCES parts(id) ON DELETE CASCADE,
  on_date TEXT NOT NULL,
  qty INTEGER NOT NULL CHECK (qty <> 0),
  unit_cost_cents INTEGER NOT NULL CHECK (unit_cost_cents >= 0),
  note TEXT NOT NULL DEFAULT ''
) STRICT;
PRAGMA user_version = 1;
```

Working with other tools
- The database is the only truth. The server keeps no rows in memory between requests: a row another tool added, changed or removed shows in the next reply.
- A request that finds the database locked by another connection waits for it for up to 3 seconds. If it is still locked after that, the reply is 503 `database busy`, nothing changes, and the server keeps running.
- Every write request happens completely or not at all. If anything unexpected fails while handling a request (a trigger another tool added, for example), the reply is 500 `internal error`, nothing that request started to change stays changed, and the server keeps running.
- Requests that arrive at the same time give the same result as if they had been handled one at a time in some order.

API
- Only the parsed JSON of a reply body matters. Every reply with a body other than the page and the script has `Content-Type: application/json; charset=utf-8`. An error reply is `{"error": "<message>"}`, where `<message>` is the text given here.
- A request's path is its request target up to the first `?`. Routes compare the path byte for byte, with no percent-decoding or normalisation. The query is ignored unless stated, and is decoded as `new URLSearchParams(query)` does; a repeated parameter means its first value.
- Any path not listed here: 404 `not found`, whatever the method. A listed path with a method not listed for it: 405 `method not allowed`.
- `<id>` in a path is any non-empty text holding no `/`. When it is not a positive integer written in ASCII digits without a leading zero, or no such row exists, the reply is 404 `part not found` or 404 `move not found`, as its route says. This includes ids too large to be any row's id.
- Before sending any reply, the server reads the whole request body, if there is one.
- A request with a body (`POST`, `PATCH`) is checked in this order, after the path's `<id>` if it has one: the media type of `Content-Type` (the part before the first `;`, spaces and tabs removed from both ends, letter case ignored) is not `application/json`, or the header is missing: 415 `content type must be application/json`. The body is longer than 10000 bytes: 413 `body too large`. The body, decoded as UTF-8 and given to `JSON.parse`, is not a JSON object: 400 `body must be a JSON object`. Then the route's own rules follow, in the order given; the first that fails decides the reply. Other keys in the body are ignored.

Parts
- A part in a reply is `{"id", "sku", "name", "on_hand", "value_cents"}`. `on_hand` is the sum of the `qty` of the part's moves, as a number. `value_cents` is the sum of `qty * unit_cost_cents` of the part's moves as a string of decimal digits (with a leading `-` when below zero, `"0"` for no moves). It is exact whatever its size, also beyond what a JavaScript number or a 64-bit integer can hold.
- `GET /api/parts`: 200 `{"parts": [...], "next": <string or null>}`. Parts are sorted by `sku` in byte order.
  - `q`: when present and not empty, only parts whose `sku` or `name` contains it, compared after `String.prototype.toLowerCase` on both sides. So `écrou` finds `ÉCROU`, and `%` and `_` are ordinary characters.
  - `after`: when present and not empty, only parts whose `sku` sorts after this text.
  - `limit`: when present, ASCII digits without a leading zero, from 1 to 100, otherwise 400 `limit must be 1 to 100`. The default is 20. The reply holds at most this many parts.
  - `next` is the `sku` of the last part in the reply when more parts match after it, otherwise `null`.
- `POST /api/parts` with `sku` and `name`: 201 and the new part.
  1. `sku` is not a string of 1 to 32 ASCII letters, digits or dashes: 400 `sku must be 1 to 32 letters, digits or dashes`.
  2. `name` is not a string, or is shorter than 1 or longer than 80 UTF-16 code units after `String.prototype.trim`: 400 `name must be 1 to 80 characters`. The part keeps the trimmed name.
  3. A part with exactly this `sku` exists (letter case matters: `ab-1` and `AB-1` are two parts): 409 `sku already exists`.
- `GET /api/parts/<id>`: 200 and the part. Unknown: 404 `part not found`.
- `PATCH /api/parts/<id>` with `name`: 200 and the part with its new name, by rule 2 above. Unknown: 404 `part not found`.
- `DELETE /api/parts/<id>`: 204 with an empty body; the part and its moves are gone. Unknown: 404 `part not found`.
- An id is never given twice, in either table, even after deletes and restarts.

Moves
- A move in a reply is `{"id", "part_id", "on_date", "qty", "unit_cost_cents", "note"}`. A positive `qty` is stock coming in; a negative one is stock going out.
- A part's running balance adds up its moves in `on_date` order, then `id` order. It may never be below zero after any move, on any date, even when a move is dated before moves already stored.
- `GET /api/parts/<id>/moves`: 200 `{"moves": [...]}`, in running-balance order, each move with an added key `balance`, the running balance after it. Unknown part: 404 `part not found`.
- `POST /api/parts/<id>/moves` with `on_date`, `qty`, `unit_cost_cents` and optionally `note`: 201 and the new move (without `balance`). Unknown part: 404 `part not found`.
  1. `on_date` is not a string `YYYY-MM-DD` (4, 2 and 2 ASCII digits) naming a real day from 2000-01-01 to 2099-12-31, where February has 29 days in years divisible by 4: 400 `on_date must be a valid YYYY-MM-DD date`.
  2. `qty` is not a whole JSON number from -1000000000 to 1000000000 other than 0: 400 `qty must be a non-zero whole number up to 1000000000`.
  3. `unit_cost_cents` is not a whole JSON number from 0 to 1000000000: 400 `unit_cost_cents must be a whole number from 0 to 1000000000`.
  4. `note` is present and is not a string of at most 200 UTF-16 code units: 400 `note must be at most 200 characters`. It is stored as given; without it the note is empty.
  5. With the new move included, the running balance goes below zero: 409 `stock would go below zero on <date>`, where `<date>` is the `on_date` of the first move at which it does.
- `DELETE /api/moves/<id>`: 204 with an empty body. Unknown: 404 `move not found`. With the move removed, the running balance goes below zero: 409 with the same message, and the move stays.
- `POST /api/transfers` with `from_part`, `to_part`, `on_date`, `qty` and `unit_cost_cents`: 201 `{"out": <move>, "in": <move>}`. It stores two moves, or neither: `out` on `from_part` with the negative `qty` and the note `transfer to <sku of to_part>`, and `in` on `to_part` with the positive `qty` and the note `transfer from <sku of from_part>`, with the same `on_date` and `unit_cost_cents`.
  1. `from_part` or `to_part` is not a JSON number that is the id of a part: 404 `part not found`.
  2. They are the same part: 400 `from_part and to_part must differ`.
  3. `on_date` as above.
  4. `qty` is not a whole JSON number from 1 to 1000000000: 400 `qty must be a whole number from 1 to 1000000000`.
  5. `unit_cost_cents` as above.
  6. The running balance of `from_part` goes below zero: 409 as above.

Page
- `GET /` answers 200 with `Content-Type: text/html; charset=utf-8` and the page. `GET /app.js` answers 200 with `Content-Type: text/javascript; charset=utf-8` and the page's script.
- The page loads the script with a `<script>` element whose `src` is exactly `/app.js`, with no `type`, `defer` or `async` attribute, placed as the last element in `<body>`. The script is a classic script (no `import` or `export`) and does its setup at once, without waiting for any load event. All the page's code is in `/app.js`: no inline script and no `on...` attributes.
- Of the browser's APIs, the script uses only `fetch` (with the `method`, `headers` and `body` options, and the reply's `status` and `json()`), `document.getElementById`, `document.createElement`, the `textContent`, `value`, `type`, `disabled`, `append`, `replaceChildren` and `addEventListener` members of elements, and `preventDefault` of events.
- The page's `<title>` and its only `<h1>` both have the text `Parts store`.
- It holds `<form id="part-form" novalidate>` with `<input type="text" id="sku">`, `<input type="text" id="name">` and `<button type="submit" id="add">` with the text `Add`. Outside the form it holds `<input type="search" id="search">`, `<ul id="part-list">`, `<button type="button" id="more">` with the text `Load more`, and `<p id="error" role="alert">`, which is empty. `#sku`, `#name` and `#search` each have their own `<label for="<id>">`, which does not contain the field, with the text `SKU`, `Name` and `Search`.
- Every value is shown as plain text, never as HTML.
- A reply has an error status when its status is not the success status of its request: 200 for `GET`, 201 for `POST` and 204 for `DELETE`. The reply's error message is the body's `error` value when the body is a JSON object whose `error` is a string, and `Request failed.` otherwise. A reply other than a 204 whose body cannot be parsed as JSON, or a request that gets no reply at all, shows `Could not reach the server.` in `#error`.
- The list: when the page loads, the script requests `/api/parts?limit=20`, with `&q=<value>` added while the value of `#search` is not empty, the value passed through `encodeURIComponent`. It replaces the content of `#part-list` with one `<li>` per part in the reply's order. Each `<li>` has exactly two child nodes: a text node with exactly the text `<sku> <name> (<on_hand>)`, and `<button type="button">` with the text `Delete`. With no parts, the list holds one `<li>` with exactly the text `No parts.` and no button. `#more` is disabled while `next` is `null` and until the first reply has arrived, and enabled otherwise.
- `Load more`: a `click` on `#more` requests the same URL with `&after=<next>` added at the end (through `encodeURIComponent`), disables `#more`, and adds the reply's parts after the ones in the list, then sets `#more` as above from the new `next`. On an error status or no reply, the list stays, `#more` is enabled again, and the message shows.
- Search: a `change` event on `#search` fetches the list again at once, from the start. The `input` event does nothing.
- List fetches overlap when a search or `Load more` starts before an earlier one has settled: only the outcome of the last one started is used. The outcome of an earlier one, an error status or no reply included, changes nothing. A list fetch that gets an error status shows the message in `#error` and leaves the list as it was; one that succeeds leaves `#error` alone.
- Adding: a submit event on the form never reloads the page (the script calls `preventDefault`). A submit while `Add` is disabled sends nothing. Otherwise the script disables `Add` and sends `POST /api/parts` with exactly the header `Content-Type: application/json` and a JSON body with the keys `sku` and `name`, holding the fields' values unchanged. `Add` is enabled again as soon as the request settles. On 201, `#error` is emptied, `#sku` and `#name` are emptied, and the list is fetched again from the start. On an error status `#error` shows the message and the fields keep their values.
- Deleting: clicking a `Delete` button disables it and sends `DELETE /api/parts/<id>` for its part; the button is enabled again when the request settles. On 204 `#error` is emptied; on another status `#error` shows the message. After either, the list is fetched again from the start. With no reply, `#error` shows `Could not reach the server.` and the list is not fetched again.
