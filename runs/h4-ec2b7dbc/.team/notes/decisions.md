# Decisions (supervisor)

- File layout (project root): `server.mjs` (backend), `public/index.html` + `public/app.js` (frontend; server reads them from the folder of server.mjs via `new URL('./public/...', import.meta.url)`, at startup or per request — read failure = 500 `internal error`), `test/*.test.mjs` (testing), `package.json` (backend), `README.md` (docs).
- package.json: `{"type":"module","scripts":{"start":"node server.mjs","test":"node --test \"test/**/*.test.mjs\""}}` — no dependencies (changed by testing, see below).
- Data file layout: `{"nextId": <int>, "bookings": [ {id,room,title,date,start,end}, ... ]}`. Validate fully on load (nextId positive integer > every id; each booking exact keys and valid fields); otherwise `cannot read data file <name>`.
- Saving: write to the data file (writeFile directly to the path; no folder creation). Serialize all mutations through one promise queue so concurrent POSTs behave sequentially. Apply in-memory change only after the write succeeded.
- Spec is in `.team/notes/spec.md` and is final. Where a line can be read two ways, take the stricter reading and note it here.
- 2026-11-03 · frontend · A rooms or list reply with status 200 whose body lacks the expected array (or a list entry that is not an object): `#error` shows `Request failed.`; the list is kept and `#room` stays empty. Why: spec is silent; never throw, never show guessed content.
- 2026-11-03 · frontend · GET requests pass `{ method: 'GET' }` explicitly; any reply with status 204 skips json() (only DELETE expects it; for GET/POST it is then an error status with `Request failed.`). Why: stricter reading of "a reply other than a 204 whose body cannot be read counts as no reply".
- 2026-11-03 · frontend · Book/Cancel re-enable runs in the request helper's `finally`, in the same tick fetch/json() settles, before the outcome is handled. Why: "enabled again as soon as the request settles, before anything else happens".
- 2026-11-03 · backend · Data file accepted only in the exact layout the server writes (exact keys, nextId > every id, unique ids, trimmed titles, no overlapping bookings); ENOTDIR (a file on the path) is not ENOENT, so it fails startup. Why: stricter reading of "not data in the layout this server writes" / "fails with ENOENT".
- 2026-11-03 · backend · Content-Type media type: ASCII-only lowercasing, trims only spaces/tabs (not String.trim). DELETE id compared as a string to stored ids, so huge ids never round onto an existing id. CONNECT is answered 404/405 on the raw socket. Why: stricter readings of rule 1, the delete id rule and "whatever the method".
- 2026-11-03 · testing · package.json test script is `node --test "test/**/*.test.mjs"`: on Node 22 `node --test test/` treats `test/` as a module and fails. Why: `npm test` must run every test file.
- 2026-11-03 · testing · Near-miss copies (`.team/near-miss/<n>-<file>`, built by `.team/tools/near-miss-make.mjs`) are swapped in and restored inside a scratch copy of the project in the OS temp folder (`.team/tools/near-miss-run.mjs`), never in the real tree. Why: other sections edit server.mjs in parallel; an in-place swap could overwrite their edits.
- 2026-11-03 · testing · Tests accept GET requests from app.js with no options or `method: 'GET'`; PORT failure stderr is checked as exactly one non-empty line with no stack trace (spec: "one line of its choice"). Why: spec leaves those free.
