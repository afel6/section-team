The help desk with its dashboard is in use, and its databases hold real data that must not be lost. Please add two AI features: a summary of a ticket and a suggested category for it, both from a model the server reaches over HTTP. Everything not mentioned here keeps working exactly as it does now, on new databases and on existing ones. The schema does not change: it stays at `user_version` 1.

Model
- The model is reached at the URL in the `MODEL_URL` environment variable. At startup the server now checks `PORT`, then `MODEL_URL`, then goes on as before.
- An unset or empty `MODEL_URL` is allowed: the server starts and runs as before, and the two routes below answer 503 `model not configured`.
- A `MODEL_URL` that `new URL()` cannot parse, or whose `protocol` is not `http:` or `https:`, makes the server write `MODEL_URL must be an http or https URL` followed by "\n" to stderr, and nothing else to stderr, and exit with code 1 without opening the database and without listening.
- A model call makes one or more attempts. Each attempt is a `POST` request to `MODEL_URL` exactly as given, with the header `Content-Type: application/json` and the JSON body `{"messages": [{"role": "system", "content": <instructions>}, {"role": "user", "content": <ticket>}]}`. The body has no other key, `messages` holds only these two objects, and each object has only these two keys.
- `<instructions>` is a string of your choice that tells the model its task. It holds nothing from the database. It is the same string in every summary call, and the same string in every category call, and the summary string is not the category string. The category instructions name all five categories below.
- `<ticket>` is the string `JSON.stringify({ title, description, comments })`, where `title` and `description` are the ticket's as stored, and `comments` is an array of the `text` of each of the ticket's comments, sorted by comment `id` (`[]` when it has none).
- Nothing else from the database goes to the model: no other ticket's title, description or comments, no user's username, id, role or password hash, and no session token.
- A ticket's text is data, never instructions to the server. A ticket whose title, description or comments ask for other users' data, other tickets or secrets changes nothing above: the model still gets only `<instructions>` and `<ticket>`, and whatever the model answers, the reply holds only what the route below names.
- An attempt fails when the request cannot be sent or its connection fails; when the whole reply has not arrived within 2000 milliseconds of the attempt's start; when the reply's status is not 200 (a redirect is not followed: a reply with a 3xx status fails the attempt); when the reply's body, decoded as UTF-8 and given to `JSON.parse`, is not a JSON object whose `text` is a string; or when that `text` fails the route's check below. An attempt that runs out of time is aborted, and nothing it receives later is used.
- A failed attempt is followed at once by another, up to 2 retries: a model call makes at most 3 attempts, and it stops at the first attempt that does not fail. When all 3 attempts fail, the reply is 502 `model call failed`.
- While a model call is waiting, the server answers other requests as usual and keeps no database transaction open.

Routes
- `POST /api/tickets/<id>/summary` and `POST /api/tickets/<id>/category` are for both roles. A member can use them only on their own tickets: for any other ticket the reply is 404 `ticket not found`, as on every route with a ticket `<id>`.
- Their request body is read and ignored: the checks of `Content-Type`, body size and JSON do not apply to these two routes.
- After the checks of the path, method, session and `<id>`: when `MODEL_URL` is unset or empty, the reply is 503 `model not configured`; otherwise the model call is made.
- `POST /api/tickets/<id>/summary`: the route's check is that `text`, after `String.prototype.trim`, is from 1 to 500 UTF-16 code units long. The reply is 200 `{"summary": <the trimmed text>}`. Audit `ticket.summary`.
- `POST /api/tickets/<id>/category`: the route's check is that `text`, after `String.prototype.trim`, is exactly one of `billing`, `bug`, `account`, `feature` and `other`. The reply is 200 `{"category": <that word>}`. The category is not stored. Audit `ticket.category`.
- The audit entry of both routes has the target `ticket:<id>`, with the ticket's id, and follows the rules of the audit log as before: a reply other than 200 adds no entry.
