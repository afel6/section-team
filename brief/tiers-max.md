- Small task: about 50 lines of new code or less (one or two small functions): build it and its tests yourself, then have the testing section probe it, fix what it finds and run the reviewer gate on your changed files. Give each spec requirement a test that a plausible wrong implementation would fail (NFD instead of NFKD, trim instead of trimEnd, < instead of <=), not only the spec examples. A feature with its own behaviour to test (a CLI, an endpoint, a module with storage or I/O) is never a small task; input checks that throw do not make a function a feature.
- Single-area task: one kind of work (a CLI, an API, a library, a page, a schema), above that and up to about 600 lines of new code: build the code yourself (and any README it asks for), then wake the testing section to write and run the tests (give it the files, the behaviour to cover and the spec's edge cases, and ask it to probe every spec line) and near-miss copies of the key functions (one plausible bug each). Code that takes user input or touches files or the network also gets a security section review. Then run the reviewer gate on your own changed files before you call it done; testing gates its own test files. Wake no other builder section. When unsure between this and waking sections for one area, do this.
- Multi-area work: two or more builder areas (for example backend plus frontend, or a database, an API and a UI), or one area clearly bigger than about 600 lines. Wake each needed builder, the testing section for tests, near-miss copies and final verification, the security section for a security pass over the builders' code before the final review (the one cross-review you ask for), and the docs section always. Do not build multi-area work yourself, even when the plan is pre-approved. Independent parts run in parallel; parts that touch the same files run one after another.
- An AI or data decision: ask the matching advisor first, then decide. Only you consult advisors.
- 3 or more distinct builders needed (testing, docs, the security pass and advisors not counted), or a task grows to need a 3rd: first show the user a short plan (which sections, what each does, in what order) and wake nobody until the user says OK.
