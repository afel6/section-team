The help desk you built is now in use, and its databases hold real data that must not be lost. Please add a dashboard to it: a reporting API and a browser page. Everything not mentioned here keeps working exactly as it does now, on new databases and on existing ones. The schema does not change: it stays at `user_version` 1.

Reports
- `GET /api/reports/summary`: 200 `{"counts": {"open": <n>, "pending": <n>, "closed": <n>}, "total": <n>}`. Each count is the number of matching tickets with that `status`, and `total` is their sum, all as JSON numbers. A matching ticket is one the session's user sees (for a member, only their own tickets, as on every ticket route) that passes every filter given.
- The filters come from the query and are checked in this order; the first that fails decides the reply:
  1. `priority`: when present and not empty, it is `low`, `normal` or `high`, otherwise 400 `priority must be low, normal or high`. Only tickets with that `priority` match.
  2. `from`: when present and not empty, it is a valid date, otherwise 400 `from must be a valid YYYY-MM-DD date`. Only tickets whose `created_at` is at or after 00:00:00.000 UTC of that day match.
  3. `to`: when present and not empty, it is a valid date, otherwise 400 `to must be a valid YYYY-MM-DD date`. Only tickets whose `created_at` is before 00:00:00.000 UTC of the day after it match.
  4. `from` and `to` are both present and not empty, and `from` is a later day than `to`: 400 `from must not be after to`.
  5. `created_by`: for an admin, when present and not empty, it is a positive integer written in ASCII digits without a leading zero, otherwise 400 `created_by must be a positive whole number`. Only tickets whose `created_by` is that id match; an id that is no user's matches none. For a member, `created_by` is ignored and never checked.
- A valid date is a string `YYYY-MM-DD` (4, 2 and 2 ASCII digits) naming a real day from 2000-01-01 to 2099-12-31, where February has 29 days in years divisible by 4.
- `GET /api/reports/chart.svg`: the same counts drawn as a bar chart, from the same tickets, with the same filters, rules and error replies. It answers 200 with `Content-Type: image/svg+xml; charset=utf-8` and a body that is well-formed XML and starts with `<svg` (no XML declaration, doctype or whitespace before it).
  - The root element is `<svg>` with `xmlns="http://www.w3.org/2000/svg"`, `width="320"`, `height="200"` and `viewBox="0 0 320 200"`.
  - The root holds exactly 7 child elements and nothing else apart from whitespace between them, in this order: `<title>` with the text `Tickets by status`, then, for each status in the order `open`, `pending`, `closed`, one `<rect>` followed by one `<text>`.
  - For the status at position `i` (0 for `open`, 1 for `pending`, 2 for `closed`) with the count `c`, where `m` is the largest of the three counts: its `<rect>` has `x` set to `20 + 100 * i`, `y` to `170 - h`, `width` to `80` and `height` to `h`, where `h` is `Math.round(150 * c / m)`, or `0` when `m` is 0. Its `<text>` has `x` set to `60 + 100 * i`, `y` to `190` and `text-anchor` to `middle`, and holds only the text `<status> <c>`, for example `open 3`.
  - Each of these numbers is written in ASCII digits, with no sign, decimal point or unit. Other attributes may be added to these elements; the attributes named here have exactly these values.

Page
- `GET /` answers 200 with `Content-Type: text/html; charset=utf-8` and the page. `GET /app.js` answers 200 with `Content-Type: text/javascript; charset=utf-8` and the page's script. These two routes need no session. The page, the script and the chart are the only replies with a body that is not JSON.
- The page loads the script with a `<script>` element whose `src` is exactly `/app.js`, with no `type`, `defer` or `async` attribute, placed as the last element in `<body>`. The script is a classic script (no `import` or `export`) and does its setup at once, without waiting for any load event. All the page's code is in `/app.js`: no inline script and no `on...` attributes.
- Of the browser's APIs, the script uses only `fetch` (with the `method`, `headers` and `body` options, and the reply's `status` and `json()`), `document.getElementById`, `document.createElement`, the `textContent`, `value`, `disabled`, `hidden`, `src`, `append`, `replaceChildren` and `addEventListener` members of elements, and `preventDefault` of events.
- The page's `<title>` and its only `<h1>` both have the text `Help desk`.
- It holds `<p id="error" role="alert">`, which is empty and is not inside `#login-form` or `#dashboard`.
- It holds `<form id="login-form" novalidate hidden>` with `<input type="text" id="username">`, `<input type="password" id="password">` and `<button type="submit" id="login">` with the text `Log in`.
- It holds `<section id="dashboard" hidden>` with `<p id="who">`, which is empty, `<button type="button" id="logout">` with the text `Log out`, `<form id="filter-form" novalidate>`, and, outside that form, `<ul id="counts">` and `<p id="total">`, both empty, and `<img id="chart" alt="Tickets by status">` with no `src` attribute.
- `#filter-form` holds `<select id="priority">` with exactly four `<option>` elements, in this order: one with `value=""` and the text `Any`, then one each for `low`, `normal` and `high`, with that word as both its `value` and its text. It also holds `<input type="date" id="from">`, `<input type="date" id="to">` and `<button type="submit" id="apply">` with the text `Apply`.
- `#username`, `#password`, `#priority`, `#from` and `#to` each have their own `<label for="<id>">`, which does not contain the field, with the text `Username`, `Password`, `Priority`, `From` and `To`.
- Every value is shown as plain text, never as HTML.
- An element is shown when its `hidden` is false and hidden when it is true. The logged-out view shows `#login-form` and hides `#dashboard`. The logged-in view for a user sets the text of `#who` to `<username> (<role>)`, hides `#login-form`, shows `#dashboard`, and starts a report fetch.
- A reply has an error status when its status is not the success status of its request: 200 for `GET` and for `POST /api/session`, and 204 for `DELETE`. The reply's error message is the body's `error` value when the body is a JSON object whose `error` is a string, and `Request failed.` otherwise. A reply other than a 204 whose body cannot be parsed as JSON, or a request that gets no reply at all, shows `Could not reach the server.` in `#error`.
- When the page loads, the script requests `GET /api/session`. On 200 it shows the logged-in view for the reply's `user`. On 401 it shows the logged-out view and leaves `#error` empty. On any other error status, or with no reply, it shows the logged-out view and the message in `#error`.
- Logging in: a submit event on `#login-form` never reloads the page (the script calls `preventDefault`). A submit while `#login` is disabled sends nothing. Otherwise the script disables `#login` and sends `POST /api/session` with exactly the header `Content-Type: application/json` and a JSON body with the keys `username` and `password`, holding the fields' values unchanged. As soon as the request settles, `#login` is enabled again and `#password` is emptied. On 200, `#error` is emptied and the page shows the logged-in view for the reply's `user`, without another request to `/api/session`. On an error status, or with no reply, `#error` shows the message and `#username` keeps its value.
- A report fetch requests `/api/reports/summary` followed by the query, built from the filter fields when the fetch starts: for `priority`, `from` and `to`, in that order, each field whose value is not empty gives `<name>=<value>`, the value passed through `encodeURIComponent`; these are joined with `&` and put after a `?`. With all three fields empty there is no `?`.
- On 200, `#counts` holds exactly three `<li>` elements, for `open`, `pending` and `closed` in that order, each with exactly the text `<status>: <count>` and no other child; `#total` has the text `Total: <total>`; the `src` of `#chart` is set to `/api/reports/chart.svg` followed by the same query; and `#error` is emptied. On an error status, or with no reply, `#error` shows the message, and `#counts`, `#total` and `#chart` stay as they were.
- When report fetches overlap, only the outcome of the last one started is used. The outcome of an earlier one, an error status or no reply included, changes nothing. A report fetch started before a successful logout changes nothing when it settles.
- Filtering: a submit event on `#filter-form` never reloads the page, and starts a report fetch at once.
- Logging out: a `click` on `#logout` disables it and sends `DELETE /api/session`; `#logout` is enabled again as soon as the request settles. On 204, `#error`, `#who`, `#counts` and `#total` are emptied and the page shows the logged-out view. On an error status, or with no reply, `#error` shows the message and the view stays as it was.
