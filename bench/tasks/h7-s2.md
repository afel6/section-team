The parts store you built is now in use, and its databases hold real data that must not be lost. Please make this change to it. Everything not mentioned here keeps working exactly as it does now, on new databases and on existing ones.

Handles
- Every part gets a `handle`: a short name for links. The part object in every reply, from every route that returns one, gains the key `handle`.
- The handle of a new part comes from its trimmed name: apply `normalize('NFKD')`, remove the combining marks U+0300 to U+036F, apply `toLowerCase`, replace every run of characters outside `a-z` and `0-9` with one `-`, remove `-` from both ends, keep the first 40 characters, and remove `-` from the end again. If nothing is left, use `part`. If that text is already the handle of a part, add `-2` to it, or else `-3`, and so on: the smallest number that gives a free handle.
- Handles are never changed by `PATCH`, and a request body cannot set one. Deleting a part frees its handle.

Schema
- The schema is now version 2. `moves` stays as it is. `parts` is exactly this, on a new database and on a migrated one:

```sql
CREATE TABLE parts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  sku TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  handle TEXT NOT NULL UNIQUE
) STRICT;
PRAGMA user_version = 2;
```

- Other tools still use this file, so the rules for tables, columns, triggers and indexes stay as they were. A database that is empty or new gets version 2 at once.

Migration
- At startup, after opening it and before listening, the server migrates a database with `user_version` 1 to version 2. A database with `user_version` 2 is used as it is. Any other database is refused as before.
- Handles are given in `id` order by the rule above, each new handle counting as taken for the parts after it.
- Everything else stays: every part and move with its id and all its values; every table, index, trigger and view another tool added to the file, still working; and the rule that an id is never given twice, also when the parts or moves with the highest ids were deleted before the migration. `moves.part_id` still references `parts(id)` with `ON DELETE CASCADE`.
- The migration happens completely or not at all. If it is killed at any moment, the file holds either the old version or the new one, intact, and the next start finishes the job.
- A version 1 database with a move whose `part_id` is not a part, or with a part whose running balance goes below zero, can only come from another tool. It is not migrated. If that or anything else stops the migration, the server writes `cannot migrate database <name>` followed by "\n" to stderr, with `<name>` as before, and exits with code 1 without listening, leaving the database's content and `user_version` as they were.
- A database of 20000 parts and 100000 moves migrates within 30 seconds.

Report
- `GET /api/report?as_of=<date>`: 200 `{"as_of": <date>, "parts": [...], "total_value_cents": <string>}`, counting only moves with `on_date` on or before that date. `parts` holds every part, sorted by `handle` in byte order, each as `{"id", "handle", "sku", "on_hand", "value_cents"}`, with `on_hand` and `value_cents` as defined for parts but counting only those moves (`0` and `"0"` when there are none). `total_value_cents` is the sum of the parts' values, written the same way and just as exact.
- `as_of` missing, or not a valid date by the rule for `on_date`: 400 `as_of must be a valid YYYY-MM-DD date`.

Page
- Each part's text node in the list becomes `<handle>: <sku> <name> (<on_hand>)`. Nothing else about the list changes.
- The page gains `<form id="report-form" novalidate>`, outside `#part-form`, with `<input type="date" id="as-of">`, its own `<label for="as-of">` that does not contain it, with the text `As of`, and `<button type="submit" id="report">` with the text `Show report`. Outside that form it gains `<ul id="report-list">` and `<p id="report-total">`, both empty.
- A submit event on that form never reloads the page and requests `/api/report?as_of=<value>`, the value of `#as-of` through `encodeURIComponent`.
- On success, `#report-list` holds one `<li>` per part in the reply's order, with exactly the text `<handle> <on_hand> <value_cents>` and no other child, and `#report-total` has the text `Total: <total_value_cents>`; `#error` is emptied. An error status or no reply shows the message in `#error`, as for other requests, and leaves the report as it was.
- When report requests overlap, only the outcome of the last one started is used. Report requests and list fetches are independent: neither one's start or outcome makes the other's outcome ignored.
