Build a help-desk app: an HTTP server `server.mjs` (an ES module, run as `node server.mjs`) that serves a JSON API with user accounts, roles, tickets, comments and an audit log, and keeps all its data in one SQLite database file through `node:sqlite`.

Server
- At startup the server checks `PORT`, then opens the database, then creates the first user if it must, then starts listening, in that order.
- It listens on 127.0.0.1 at the port in the `PORT` environment variable. An unset or empty `PORT` means 3000. A `PORT` that is not made only of ASCII digits 0-9, or whose value is above 65535, or a port that cannot be bound, makes the server write one line of its choice to stderr and exit with code 1.
- Once listening, it prints `listening on http://127.0.0.1:<port>` followed by "\n" to stdout, where `<port>` is the port actually bound (with `PORT=0`, the port the OS picked). This line is the only thing the server ever writes to stdout.
- The database is the file named by the `DB_FILE` environment variable. An unset or empty `DB_FILE` means `helpdesk.db`. A relative `DB_FILE`, the default included, is resolved against the current working directory.
- A file that does not exist, or is empty, or is a database with no tables and `user_version` 0, gets the schema below. A database with `user_version` 1 is used as it is, apart from the first user below. Anything else (the file or a folder on its path cannot be opened or created, the file is not a SQLite database, or it is a database with any other `user_version`, or with `user_version` 0 and tables in it) makes the server write `cannot open database <name>` followed by "\n" to stderr, where `<name>` is the value of `DB_FILE` as given (`helpdesk.db` when it is unset or empty), and exit with code 1 without listening and without changing the file.
- The first user: when the table `users` has no row (a new database included), the server creates the user `admin` with the role `admin` and the password held in the `ADMIN_PASSWORD` environment variable, used as given. The schema of a new database and this user are written in one transaction. When `users` has a row, `ADMIN_PASSWORD` is ignored.
- When the server must create the first user and `ADMIN_PASSWORD` is unset or is not 12 to 200 UTF-16 code units long, it writes `ADMIN_PASSWORD must be 12 to 200 characters` followed by "\n" to stderr and exits with code 1 without listening and without writing to the database: the file keeps the content it had, and a file that did not exist is either not created or left empty.
- In each of these startup failures, the line given is the only thing the server writes to stderr.

Schema
These tables are a contract: other tools read and write this file. Create exactly these tables and columns, with no other tables, columns or triggers (indexes of your own are fine).

```sql
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('admin', 'member'))
) STRICT;
CREATE TABLE sessions (
  token_hash TEXT PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  expires_at INTEGER NOT NULL
) STRICT;
CREATE TABLE login_failures (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL,
  at INTEGER NOT NULL
) STRICT;
CREATE TABLE tickets (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('open', 'pending', 'closed')),
  priority TEXT NOT NULL CHECK (priority IN ('low', 'normal', 'high')),
  created_by INTEGER NOT NULL REFERENCES users(id),
  created_at INTEGER NOT NULL
) STRICT;
CREATE TABLE comments (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ticket_id INTEGER NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  user_id INTEGER NOT NULL REFERENCES users(id),
  text TEXT NOT NULL,
  created_at INTEGER NOT NULL
) STRICT;
CREATE TABLE audit (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  at INTEGER NOT NULL,
  user_id INTEGER NOT NULL REFERENCES users(id),
  action TEXT NOT NULL,
  target TEXT NOT NULL
) STRICT;
PRAGMA user_version = 1;
```

- Every time in the database and in replies (`expires_at`, `at`, `created_at`) is a whole number of milliseconds since 1970-01-01T00:00:00Z. A request's time is one reading of `Date.now()` taken while the request is handled; every time the request stores or compares is that reading.

Working with other tools
- The database is the only truth. The server keeps no rows in memory between requests: a row another tool added, changed or removed shows in the next reply. This holds for users, sessions and recorded failed logins too.
- A request that finds the database locked by another connection waits for it for up to 3 seconds. If it is still locked after that, the reply is 503 `database busy`, nothing changes, and the server keeps running.
- Every write request happens completely or not at all. If anything unexpected fails while handling a request (a trigger another tool added, for example), the reply is 500 `internal error`, nothing that request started to change stays changed, and the server keeps running.
- Requests that arrive at the same time give the same result as if they had been handled one at a time in some order.

API
- Only the parsed JSON of a reply body matters. Every reply with a body has `Content-Type: application/json; charset=utf-8`. An error reply is `{"error": "<message>"}`, where `<message>` is the text given here.
- A request's path is its request target up to the first `?`. Routes compare the path byte for byte, with no percent-decoding or normalisation. The query is ignored unless stated, and is decoded as `new URLSearchParams(query)` does; a repeated parameter means its first value.
- `<id>` in a path is any non-empty text holding no `/`. When it is not a positive integer written in ASCII digits without a leading zero, or no such row exists, the reply is 404 `user not found` or 404 `ticket not found`, as its route says. This includes ids too large to be any row's id.
- Every route needs a session except `POST /api/session`. A route marked (admin only) is for users with the role `admin`; every other route is for both roles.
- Before sending any reply, the server reads the whole request body, if there is one.
- Each request is checked in this order, and the first check that fails decides the reply:
  1. Its path is not listed here: 404 `not found`, whatever the method.
  2. Its method is not listed for its path: 405 `method not allowed`.
  3. Its route needs a session and the request has none: 401 `login required`.
  4. Its route is marked (admin only) and the session's user has the role `member`: 403 `forbidden`.
  5. The path's `<id>`, if it has one, as above.
  6. A `POST` or `PATCH` request: the media type of `Content-Type` (the part before the first `;`, spaces and tabs removed from both ends, letter case ignored) is not `application/json`, or the header is missing: 415 `content type must be application/json`. The body is longer than 100000 bytes: 413 `body too large`. The body, decoded as UTF-8 and given to `JSON.parse`, is not a JSON object: 400 `body must be a JSON object`.
  7. The route's own rules, in the order given.
- A key is present when the body object has it, whatever its value (`null` included). Keys a route does not name are ignored.

Accounts and sessions
- A user in a reply is `{"id", "username", "role"}`, with nothing else in it.
- A password is stored only in `users.password_hash`, as `scrypt$<salt>$<key>`: `<salt>` is 16 bytes from `crypto.randomBytes`, and `<key>` is what `crypto.scrypt` (or `crypto.scryptSync`) from `node:crypto` derives from the password's UTF-8 bytes with those 16 bytes as the salt, a key length of 64 and the default options; both are written as lowercase hex. Every password stored, a changed one included, gets a new salt. A password matches when the key derived from it with the stored salt equals the stored key.
- A session token is 32 bytes from `crypto.randomBytes`, written as 64 lowercase hex characters. The database stores only its hash, in `sessions.token_hash`: the lowercase hex SHA-256 (`crypto.createHash('sha256')`) of the token's 64 hex characters as text, not of its 32 bytes. A session's `expires_at` is the time of its login request plus 28800000 (8 hours).
- A request's token is read from its `Cookie` header: the header's value is split at every `;`, spaces and tabs are removed from both ends of each piece, and the first piece that starts with `sid=` holds the token, the text after `sid=`. The request has a session when the hash of that token is the `token_hash` of a row in `sessions` whose `expires_at` is above the request's time. Without a `Cookie` header, without a piece starting with `sid=`, or without such a row, it has none.
- `POST /api/session` (no session needed: a session the request has is ignored and stays) with `username` and `password`: 200 `{"user": <user>}` with the header `Set-Cookie` holding exactly `sid=<token>; Path=/; HttpOnly; SameSite=Strict; Max-Age=28800`, where `<token>` is the token of a new session for that user. Every `login_failures` row with this `username` is deleted. Audit `login`.
  1. `username` or `password` is not a string: 400 `username and password must be strings`.
  2. `login_failures` holds 5 or more rows with exactly this `username` and an `at` above the request's time minus 900000 (15 minutes): 429 `too many login attempts`. The password is not checked and nothing is recorded.
  3. No user has exactly this `username`, or the password does not match: 401 `wrong username or password`. The failure is recorded as a new `login_failures` row with this `username` and `at` the request's time, although the reply is an error.
- `GET /api/session`: 200 `{"user": <user>}`, the session's user.
- `DELETE /api/session`: 204 with an empty body and the header `Set-Cookie` holding exactly `sid=; Path=/; HttpOnly; SameSite=Strict; Max-Age=0`. This session's row is deleted; the user's other sessions stay. Audit `logout`.
- The 200 of `POST /api/session` and the 204 of `DELETE /api/session` are the only replies with a `Set-Cookie` header.

Users
- `GET /api/users` (admin only): 200 `{"users": [...]}`, every user, sorted by `id`.
- `POST /api/users` (admin only) with `username`, `password` and `role`: 201 and the new user. Audit `user.create`.
  1. `username` is not a string of 3 to 32 characters, each one of `a` to `z`, `0` to `9` and `_`: 400 `username must be 3 to 32 lowercase letters, digits or underscores`.
  2. `password` is not a string of 12 to 200 UTF-16 code units: 400 `password must be 12 to 200 characters`. It is used as given, not trimmed.
  3. `role` is not `admin` or `member`: 400 `role must be admin or member`.
  4. A user with this `username` exists: 409 `username already exists`.
- `PATCH /api/users/<id>` (admin only) with `password`, `role` or both: 200 and the user with the values given changed. Unknown: 404 `user not found`. When the change succeeds, every row in `sessions` whose `user_id` is that user's id is deleted, also when that user is the one making the request. Audit `user.update`.
  1. Neither `password` nor `role` is present: 400 `nothing to change`.
  2. `password` is present and breaks rule 2 of `POST /api/users`: 400 as there.
  3. `role` is present and breaks rule 3 of `POST /api/users`: 400 as there.
  4. With the change made, no user would have the role `admin`: 409 `cannot remove the last admin`.

Tickets
- A ticket in a reply is `{"id", "title", "description", "status", "priority", "created_by", "created_at"}`. `created_by` is the id of the user who created it.
- A member's own tickets are the ones whose `created_by` is the member's id. To a member, every other ticket does not exist: each route with a ticket `<id>` answers 404 `ticket not found` for it, and lists leave it out. An admin sees every ticket.
- `GET /api/tickets`: 200 `{"tickets": [...], "next": <number or null>}`, newest first (`id` descending).
  - `limit`: when present, ASCII digits without a leading zero, from 1 to 100, otherwise 400 `limit must be 1 to 100`. The default is 50. The reply holds at most this many tickets.
  - `before`: when present, a positive integer written in ASCII digits without a leading zero, otherwise 400 `before must be a positive whole number`. Only tickets whose `id` is below it are listed.
  - `limit` is checked before `before`.
  - `next` is the `id` of the last ticket in the reply when more tickets match after it, otherwise `null`.
- `POST /api/tickets` with `title`, `description` and optionally `priority`: 201 and the new ticket, with `status` `open`, `priority` as given or else `normal`, `created_by` the session's user and `created_at` the request's time. Audit `ticket.create`.
  1. `title` is not a string, or is shorter than 1 or longer than 120 UTF-16 code units after `String.prototype.trim`: 400 `title must be 1 to 120 characters`. The ticket keeps the trimmed title.
  2. `description` is not a string, or is shorter than 1 or longer than 5000 UTF-16 code units after `String.prototype.trim`: 400 `description must be 1 to 5000 characters`. The ticket keeps the trimmed description.
  3. `priority` is present and is not `low`, `normal` or `high`: 400 `priority must be low, normal or high`.
- `GET /api/tickets/<id>`: 200 and the ticket. Unknown: 404 `ticket not found`.
- `PATCH /api/tickets/<id>` with any of `title`, `description`, `status` and `priority`: 200 and the ticket with the values given changed. Unknown: 404 `ticket not found`. Audit `ticket.update`.
  1. None of these four keys is present: 400 `nothing to change`.
  2. The session's user has the role `member` and `status` or `priority` is present: 403 `forbidden`.
  3. `title` is present and breaks rule 1 of `POST /api/tickets`: 400 as there.
  4. `description` is present and breaks rule 2 of `POST /api/tickets`: 400 as there.
  5. `status` is present and is not `open`, `pending` or `closed`: 400 `status must be open, pending or closed`.
  6. `priority` is present and breaks rule 3 of `POST /api/tickets`: 400 as there.
- `DELETE /api/tickets/<id>` (admin only): 204 with an empty body; the ticket and its comments are gone. Unknown: 404 `ticket not found`. Audit `ticket.delete`.

Comments
- A comment in a reply is `{"id", "ticket_id", "user_id", "text", "created_at"}`. `user_id` is the id of the user who wrote it.
- `GET /api/tickets/<id>/comments`: 200 `{"comments": [...]}`, every comment of the ticket, sorted by `id`. Unknown ticket: 404 `ticket not found`.
- `POST /api/tickets/<id>/comments` with `text`: 201 and the new comment, with `user_id` the session's user and `created_at` the request's time. Unknown ticket: 404 `ticket not found`. Audit `comment.create`.
  1. `text` is not a string, or is shorter than 1 or longer than 2000 UTF-16 code units after `String.prototype.trim`: 400 `text must be 1 to 2000 characters`. The comment keeps the trimmed text.
  2. The ticket's `status` is `closed`: 409 `ticket is closed`.
- An id is never given twice, in any table, even after deletes and restarts.

Audit log
- An entry in a reply is `{"id", "at", "user_id", "action", "target"}`.
- Each route above that names an audit action adds exactly one entry to `audit` when it succeeds, in the same transaction as its other changes, with `at` the request's time, `user_id` the session's user (for `login`, the user who logged in), `action` the name given, and this `target`:
  - `login` and `logout`: `user:<id>`, with the id of that user.
  - `user.create` and `user.update`: `user:<id>`, with the id of the user created or changed.
  - `ticket.create`, `ticket.update` and `ticket.delete`: `ticket:<id>`, with the ticket's id.
  - `comment.create`: `comment:<id>`, with the new comment's id.
- A request whose reply has a status of 400 or above adds no entry, and no other request adds one. Creating the first user at startup adds none.
- `GET /api/audit` (admin only): 200 `{"entries": [...], "next": <number or null>}`, newest first (`id` descending), with `limit`, `before` and `next` working as for `GET /api/tickets`, entries in place of tickets.
- No route changes or removes an entry.

Secrets
- No reply holds a password, a password hash or a session token, with one exception: the `Set-Cookie` header of a successful login holds that login's new token.
- While running, the server may write lines of its choice to stderr. Nothing it writes to stdout or stderr ever holds a password, a password hash or a session token.
- The database holds a password only as its `password_hash` and a session token only as its `token_hash`.
