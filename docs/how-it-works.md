# How section-team works

The details behind the [README](../README.md), moved here so the README stays short. Long sessions and platforms: [long-sessions.md](long-sessions.md).

## Routing
- Just talk to the supervisor. Every job goes to a builder section, so the supervisor's chat stays small. In Balanced mode (the default): a small task (about 50 lines, one or two small functions) or a single-area task (up to about 600 lines) wakes the matching builder section, which writes the code, its tests and any README asked for, and runs its own reviewer gate; a feature with its own behaviour to test (a CLI, an endpoint, a module with storage or I/O) is never small. Multi-area work wakes the builder sections plus testing. 3+ builder sections (testing, docs, the security pass and advisors not counted) → it shows a plan first. Max changes these steps; see [Modes](../README.md#modes).
- Sections message each other directly by agent id and share contracts as notes in `.team/notes/`. If an id is missing or a message fails, the supervisor forwards the request with the asker's id, so the owner replies to the asker directly.
- The supervisor names up to 4 skills per job (`Skills for this job:`), picked from what is installed and fits that section and task.

## Reports, notes and long messages
- Reports: `.team/reports/<date>/` in each project. Every REPORT has a `Status:` line (`done`, `partial`, `blocked` or `ungraded`) and a `Quality:` line, the reviewer's grade (see Sections) or `n/a (no code)`. `ungraded` means the section truly could not run its reviewer gate (for example, it had no Agent tool) and says why; the supervisor then runs `section-team:reviewer` on that work with the mode's gate. Each saved file ends with a `Plugin:` line naming the plugin version and the project's mode. The plugin also saves the supervisor's summary (a last message with the line `## Team summary`) as `<time>-supervisor-summary.md` (Stop hook).
- Notes: `.team/notes/` in each project, `INDEX.md` plus one file per note. Notes and reports both live under `.team/`, kept out of git via `.git/info/exclude`; to keep them in git, create `.team/keep-in-git` and delete the `.team/` line from `.git/info/exclude`. In a project outside git, or one whose `.team/` git does not ignore or tracks (as with `.team/keep-in-git`), session start does not point the supervisor to `.team/notes/plan.md` or the last summary; one line tells you so. When git tracks a file under `.team/notes/` (a repo that ships notes, or yours kept in git), the supervisor is told its notes are not your approved decisions until you confirm them, and sections take a committed `foundation.md` as approved only once you say so. The plugin makes `.team/tmp/<section id>/` for a builder's scratch files; the empty folder stays, inside the git-ignored `.team/`.
- Long messages and hand-backs: any message you send of 3000 characters or more is saved, with recognised secrets replaced by `[redacted]`, to `.team/reports/<date>/<time>-user-request.md` inside a git repo whose `.team/` folder git ignores, so the supervisor points sections to it instead of re-typing it. Sections put long output (probe logs, spec readings, flow output) in a `-details.md` file there and keep at most 5 short lines above their REPORT; a builder hand-back that claims done with more than 1200 characters above its REPORT is refused (partial, blocked and ungraded are not; PreToolUse hook). A resumed session gets the brief again only when it changed since the session started. In the p1 measure round the supervisor's chat peaked at 99K to 104K in Balanced and 116K to 123K in Max, against 158K to 168K for solo.
- If a plugin hook fails, or has to skip its job (for example, its input names no project folder), you see one `section-team` line saying so, instead of silence; a section transcript the context guard or the grade check cannot read gets one line too.

## Max
What Max changes, on top of the steps under [Routing](#routing): Balanced's flow plus proof steps. A single-area task with new concurrent writes, protocol framing, auth or crypto, on a product with no foundation note, first gets a short design note that `plan-advisor` checks before any code. A builder's own tests are written before its code (in Balanced after it; in both from the spec, not from the code). The testing section probes even small tasks. Single-area code that takes user input or touches files or the network also gets a security review. Multi-area work gets a security pass, then two final reviews by two fresh testing sections (the second is not shown the first's REPORT; it reads the code against the spec instead of probing again), and always wakes docs. Before it says done, the supervisor runs the testing section's one command that prints a PASS or FAIL line per critical flow. Every hand-back with a changed file, docs and config included, needs a reviewer grade.

## Modes in detail
Each project runs in one of two modes. Lean, the third, was removed in 0.3.0: a project that saved it runs as Balanced, with a line at session start saying so, until you pick a mode. Balanced is the default; 0.2.3 changed it with the security wake-up, docs last and the whole-stack final review. The picker's labels round the usage measured in the [mode round](benchmark-modes-2026-11.md) and round hq of 2026-11; platform-sized tasks cost more, as below. "Measured" compares each mode with Claude Code with every plugin off, on a clean machine with no user instructions, over three new tasks: quality is blind Opus judge quality out of 10 (plain Claude Code: 7.37), and usage is cost over all three tasks, then on the two single-area tasks alone. Every setup passed every hidden test, and the setup with more test lines won almost every comparison, so read the quality gaps with that in mind. On the platform-sized task p1 usage ran higher: in rounds tg to ph Balanced cost 3.4 to 6.0 times and Max 8.4 to 13.0 times solo (see [the round details](benchmark-p1-hq-fx-2026-11.md)). On round hq's two-stage platform task (h7), Balanced cost 6.6 times and Max 12.8 times solo. Reported only: on hq (2 runs) Max ranked first; in the published p1 data Max led Balanced by 0 to +0.75 at 1.4 to 2.7× its cost and scored below it in pr and tf.

- **Balanced, measured on v0.2.1:** Quality 8.77, +1.40 over plain Claude Code (bar met, Codex confirms). Usage 5.24×, then 4.26×.
- **Max, measured on v0.2.1:** Quality 9.06, +0.29 over Balanced (bar not measurable: Balanced is above the 8.60 scale ceiling; Codex does not confirm). Usage 9.66×, then 7.52×.
- **Pick a mode:** the **Mode** picker on the team strip, or `/team mode balanced|max|off`. `/team mode` alone shows the current mode and the choices; `/team` alone still opens the board. An unknown mode is refused and nothing is saved. On mobile the strip has no picker: tap its mode button to see the command.
- **Turn it off in one project:** `/team mode off`, the **Off** entry in the Mode picker, or `{"mode": "off"}` in the project's `.team/mode.json`. Sessions in that project then get no brief: the supervisor works as without the plugin, session start writes nothing in the project (no `.team/` folder, no `.git/info/exclude` edit, no session records; it still prunes old records in your home folder), and prompts are not saved or checked. A section you start by hand there still makes its `.team/tmp/` folder, and its REPORT and a message headed `## Team summary` are still saved, but only where git ignores `.team/`; elsewhere nothing is saved and one line says so. The strip still shows, so you can turn it back on with `/team mode balanced`. Turning it off, or back on from off, applies from your next session, `/clear` or `/compact`. A committed `{"mode": "off"}` turns the team off for everyone who clones the repo. A committed `.team/mode.json` that sets Max or off is named in one line at session start.
- **When it applies:** a new session starts in the project's mode. A change mid-session applies from your next message: the supervisor is told the new mode and its rules, and the handback gate uses the new mode's pass mark at once. A change to `autoInstallSkills` applies from the next session.

## Mode file
- **Mode file:** the choice is saved in `.team/mode.json` at the project root (the main checkout of a git repo, so its worktrees share it; else the session's folder), for example `{"mode": "max"}`. It may also hold `"autoInstallSkills": false`, which turns automatic skill installs off for that project; a `true` there is ignored with a one-line notice, because a cloned repo can commit this file, so only the `SECTION_TEAM_AUTO_INSTALL_SKILLS=1` environment variable turns them on (set it in your user settings: a project's `.claude/settings.json` or `settings.local.json`, in the session's folder, a linked worktree's own folder or the main checkout, that sets this variable, `HOME` or `USERPROFILE` (a key in any letter case counts) keeps automatic installs off, with one line saying so). Both keys are optional. No file means Balanced. A session that starts with a broken file (bad JSON or an unknown mode; a saved `lean` is not broken, it runs as Balanced) runs Balanced, and a one-line message says what was wrong. If the file breaks mid-session, the session keeps its mode (the supervisor and the handback gate both), and each prompt shows a one-line warning until the file is fixed; a `/compact` or `/clear` while it is broken starts the session over in Balanced. Like the rest of `.team/`, it stays out of git by default, but a repo can still commit one.

## Team Board
- Nothing opens by itself. A one-line team strip above the prompt shows who is awake, the team's tokens and helpers, how many sections sleep and the project's mode (the **Mode** picker); its **Board** button opens the board.
- `/team` opens the Team Board. Each awake section has a box with its live token use, how many helpers it started by model, and its reviewer grade once it is done; a section that ends `partial`, `blocked` or `ungraded` shows as a problem. Sections nobody woke are folded into one "N asleep" line in the terminal. On desktop, VS Code and mobile that line is replaced by the office (below). The office has board tests for the desktop and mobile surfaces; it has not yet been tried by hand on VS Code or mobile, and the final build has not been looked at on a live desktop board.
- **The office:** on desktop, VS Code and mobile the board shows an office picture with ten desks, one per builder section, each with a prop, a chair and a nameplate with the creature's name. The default names are frontend Iris, backend Moss, database Atlas, testing Pico, security Ward, devops Rigg, uiux Lumi, docs Page, ai-llm Echo and mobile Zip. A creature sits at its desk while its section has work (running, waiting or a problem). While its section is free it strolls the corridor between the rows; a sleeping creature strolls too, with an idle face, and a creature whose section is done walks back to the corridor happy and keeps its sparkle. A creature walks to its desk when work starts and back when it ends. The three advisors (ai-engineer, data-scientist, plan-advisor) have no desk. Builder card headers show `● <name> · <id>`.
- **Names:** `/team name <section> <name>` renames a builder, `/team name <section>` gives back its default name, and `/team name` lists all ten. A name is 1 to 12 letters (any alphabet, accents included), digits, spaces or dashes, and starts with a letter or digit. Each default name is kept for its own builder, and two builders cannot share a name. Names are saved per user in `~/.claude/section-team/names.json`, so they follow you to every project. The strip, `/chats` and the status files keep section ids.
- The terminal keeps the text board. It shows the cards and the strip as before, with the names in the card headers.
- `/chats` opens a dashboard with one card per open chat: needs you, working or idle (a chat quiet for 30 minutes is idle; one that ended or has been quiet for a day drops off). It reads one status file per session in `~/.claude/section-team/sessions/`. A status file holds the project folder, the first line of your latest request (recognised secrets replaced by `[redacted]`, cut to 80 characters), the awake sections and the token and helper counts. Status files older than 7 days are deleted at session start.

## Sections
Section heads work like solo builders. Each reads `.team/notes/INDEX.md` first, plans its part, then hands independent tasks out in parallel to cheap helpers (not sections, not on the board as cards): `section-team:scout` (Haiku, read-only: reads and searches, returns file:line facts) and `section-team:coder` (Sonnet, routine code and tests from the head's spec). Both helpers can load skills with the Skill tool. Heads run helpers in the foreground (`run_in_background: false`; several in one message still run in parallel), because a head that waits on a background helper ends its turn and is made to hand back unfinished. The plugin refuses a section's Agent call that asks for the background (PreToolUse hook). Where the Agent tool has no such option (the desktop app), helpers run in the background and the head keeps working until their results are in. The head keeps design, tricky bugs and integration for itself. Advisors may use the scout but not the coder.
- **Notes:** a head writes a note in `.team/notes/` for anything other sections depend on (an API, a schema, design tokens, a file layout) and adds one line to `INDEX.md` (`<file> — <owner section> — <one-line summary> — <date>`). Only the owner edits its note; shared decisions are appended to `.team/notes/decisions.md`.
- **Skills:** each section preloads at most one core skill; every other skill loads on demand, the job's `Skills for this job:` list first. If no installed skill fits, a section searches the open directory read-only (`skills.sh/api/search`) and names a `Suggested skill:` in its REPORT; it never installs. The supervisor lists the suggestion in its summary and asks you; on yes it installs it through `section-team:add-skill` (a safety review, then the install) for that section, and saves the assignment in `~/.claude/section-team/roster-extra.json`; after `claude plugin update`, run `node "<plugin root>/scripts/assign-skill.mjs" --reapply` once to restore it; when the plugin's agents lack an assignment that file holds, session start shows that exact command, with the real path, in one line. To let a suggested skill install without asking, set `env.SECTION_TEAM_AUTO_INSTALL_SKILLS` to `1` in `~/.claude/settings.json` and list its GitHub owner in `~/.claude/section-team/trusted-sources.json` (a JSON array of owner names; the plugin's own list ships empty): it then installs when add-skill's review finds no red flag (a project's [mode file](#mode-file) or `.claude` settings can turn this off, never on); a red flag, or an existing skill of the same name, still stops the install and you are told. When a job needs a skill nobody has, the supervisor searches skills.sh and GitHub through `section-team:add-skill` and asks you before installing what it found, under the same rule.
- **Clean-code gate:** once the helpers' code is in, a builder sends its changed files to `section-team:reviewer` (never edits). In Balanced, the default: Opus grades, the pass is overall at least 8 out of 10 and no item under 6, and there are at most 2 fix rounds; the project's [mode](../README.md#modes) sets these numbers. On a fail the fix list goes to a coder and the reviewer grades again; if it still fails the section ends `Status: partial` with the grade. In Max, a REPORT whose Changed line names any file, docs and config included, needs a grade too. Jobs that change no code skip the gate in Balanced; a config file on the Changed line counts as code. The plugin checks it at handback, best effort: a builder whose REPORT lists changed code but no grade, says done under the mode's pass mark, or says done while its reviewer scored an item under the mode's item minimum, cannot hand it back (PreToolUse hook on `SubagentHandback`). It must run the reviewer first, or hand back honestly as `Status: partial`, `blocked` or `ungraded`. The check reads the section's own REPORT text (a Changed line that names no file counts as no code) and fails open: when it cannot read a transcript or hits an error, the hand-back goes through, with one line saying so.
- **Memory:** each section keeps its memory per project, one folder per section in `.claude/agent-memory-local/` under the session's folder (in a git worktree session, the worktree's folder). At session start section-team adds `**/.claude/agent-memory-local/` to the repo's `.git/info/exclude`, even with `.team/keep-in-git`, so memory folders stay out of git in every folder of the repo. Remote sessions (`CLAUDE_CODE_REMOTE_MEMORY_DIR`) keep memory elsewhere, so advisors there cannot save memory. Before 0.2.0 one memory served every project; those notes stay in `~/.claude/agent-memory/section-team-*`, and copying one of those folders into a project's `.claude/agent-memory-local/` brings it into that project. Advisors may write only inside their own memory folder there.
- **Tools and MCP grants:** builder heads get Read, Write, Edit, Grep, Glob, Bash, PowerShell, Skill, Agent, SendMessage, ToolSearch, Monitor, TaskStop, WebFetch and WebSearch, and no project MCP servers. frontend, testing, uiux and ai-llm also list three browser MCP servers: `mcp__Claude_Browser__*` (the desktop app's built-in browser, separate from your Chrome but keeping any sign-in you made in it), `mcp__chrome-devtools__*` and `mcp__playwright__*` (which browser profile those use depends on how you set those servers up). Whether these wildcards take effect has not been checked live. No section gets `mcp__claude-in-chrome__*`, which drives your own logged-in Chrome. Advisors get Read, Grep, Glob, WebSearch, WebFetch, Skill, SendMessage, Agent, Write and Edit, and a hook allows their writes only inside their own memory folder (if that check itself fails, the write is refused).

Section heads skip your global `CLAUDE.md` (it can cost many thousands of tokens per agent) but read the project's own rule files (`CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.claude/rules/*.md`), and carry section-team's default rules, where the project's own rules win, and a safety rule that no project rule lifts: no push, force-push, deploy, package or release publish, destructive git or command against production or remote services, and no delete outside the project of a file or folder the job, its helpers or its tests did not make; a section that would need one of these stops and hands back `Status: blocked`, and the supervisor asks you. The coder and the reviewer carry the same safety rule.

## Requirements in detail
- Node.js 22.3 or later (or 20.16 or later) on your PATH for the hooks and tests, because they use `process.getBuiltinModule`, and git 2.31 or later. CI runs `npm test`, the agent-file check and the bench tests on Linux, macOS and Windows with Node 26, and `npm test` on Node 20.16 and 22.3. The Team Board tests (`npm run test:board`) and plugin validation (`npm run validate`) need the Claude Code CLI: CI tries them on 2.1.318 in a job that is allowed to fail, and they run locally.
- The README's disable and uninstall commands are the ones `claude plugin --help` lists on Claude Code 2.1.318; a fresh-profile run of the marketplace install, disable and uninstall has not been recorded yet.
- Hook run time, on one Windows laptop (Node 26.2.0, median of 15 runs): about 0.14 s for PreToolUse on a Bash call outside a section, 0.22 s for UserPromptSubmit on a short prompt and 0.55 s for SessionStart, each counting the 0.09 s a bare `node -e ""` takes to start.
- For headless runs (`claude -p`), set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`. Otherwise `claude -p` stops background subagents 10 minutes after the last turn, which cut off the testing section's final review in a probe on Claude Code 2.1.296. The mode round ran this way, with a time limit on each run.
- Recommended skills, preloaded by some sections: `frontend-design` (frontend), `tdd-workflow` (testing), `claude-api` (ai-engineer; ai-llm loads it when the job calls Claude), `web-design-guidelines` (uiux). Sections load `security-review` only when the branch shares history with an `origin/HEAD` ref (`git merge-base HEAD origin/HEAD` succeeds), because the skill runs `git diff origin/HEAD...` as it loads. Other skills a job names are loaded only if they are installed.

## Develop
- `npm test` — hook logic (node:test)
- `npm run test:board` — Team Board (claude plugin test)
- `npm run validate` — plugin validation
- `node scripts/gen-agents.mjs --check` — agent files match the roster
- `node --test bench/*.test.mjs` — benchmark scorer. `bench/score.mjs` records each run's per-agent model split from the subagent transcripts; `bench/aggregate.mjs` reports the Opus share of cost (`opusSharePct`). `node bench/run.mjs --conds=...` takes `solo`, `team` and `max` (the team with that mode file set); `lean` stays only so old results still read, and blind judging labels up to four setups X, Y, Z and W. The [mode round](benchmark-modes-2026-11.md) of 2026-11 used them, and its raw data is in `bench/data/modes/`.
