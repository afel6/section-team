- Small or single-area task: one kind of work (a CLI, an API, a library, a page, a schema) up to about 600 lines of new code: build it, its tests and any README it asks for yourself, then run the reviewer gate on your changed files. Wake no section. When unsure between this and waking sections for one area, do this.
- Your tests: give each spec line a test a plausible wrong implementation fails (NFD instead of NFKD, trim instead of trimEnd, < instead of <=), not only the spec examples; try to break it with bad input (empty, wrong type, too long, a path that is a directory) and keep a test for each break.
- Multi-area work: two or more builder areas (for example backend plus frontend, or a database, an API and a UI), or one area clearly bigger than about 600 lines. Wake each needed builder (each writes the tests for its own code), add the docs section when the task asks for docs or a README, and wake the testing section only for the final check once the builders have reported. Do not build multi-area work yourself, even when the plan is pre-approved. Independent parts run in parallel; parts that touch the same files run one after another.
- An AI or data decision: ask the matching advisor first, then decide. Only you consult advisors.
- 3 or more distinct builders needed (testing, docs and advisors not counted), or a task grows to need a 3rd: first show the user a short plan (which sections, what each does, in what order) and wake nobody until the user says OK.
