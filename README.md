# section-team

[![test](https://github.com/afel6/section-team/actions/workflows/test.yml/badge.svg)](https://github.com/afel6/section-team/actions/workflows/test.yml) [![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

A Claude Code plugin that turns every session into a **supervisor** of a small engineering team. The supervisor plans and routes; every job goes to a specialist builder **section** (frontend, backend, database, testing, security, devops, uiux, docs, ai-llm, mobile), and two read-only advisors advise it. Code goes through a **reviewer gate** before it is handed back, and work that cannot pass is handed back marked partial or ungraded. Each project picks how much the team does with one of two **modes** (Balanced or Max), section reports are saved in the project, and a live **Team Board** shows who is working.

## Results
Measured over 17 benchmark rounds (three tasks of rising size, two runs each, graded blind by 12 Opus judges per round). In the final round:

| | Cost per task | Judge quality (1–10) | Ranked 1st / last (of 12 judges) |
|---|---|---|---|
| Plain Claude Code (plugin off) | $0.85 | 7.1 | 0 / 9 |
| An earlier version of this team | $3.39 | 7.7 | 0 / 3 |
| **section-team (round 17)** | $3.10 | **8.6** | **12 / 0** |

Across the later pre-registered rounds, the default mode cost about 2.2 to 5.2 times as much as plain Claude Code, and about 7.5 to 9.7 times in Max, depending on the tasks and the setup (the Max range comes from the mode round only, which also measured Lean, removed in 0.3.0; see [Modes](#modes)), for code that blind judges rated higher, with tests the largest part of the gap (42 to 44% in the mode round). On the multi-area task, the one closest to a real platform, the mode round measured Lean 4.5, Balanced 7.0 and Max 13.4 times plain Claude Code ([details](docs/benchmark-modes-2026-11.md)). The table above is the final tuning round; the later rounds on new tasks are the fairer guide.

**Limits:** every setup, plain Claude Code included, passed all the hidden tests, so the gains are in blind-judged quality, not in whether the code works. Each cell is 2 runs (about ±0.3 judge noise), and the team was tuned over 17 rounds on these same three tasks. A pre-registered held-out round on three new tasks it had never seen measured a smaller gain that still cleared the bar set in advance: blind judge quality 8.8 against 8.2 for plain Claude Code, both passing every hidden test, at about 2.2 times the cost ([details](docs/benchmark-heldout-2026-11.md)). A later pre-registered round on a clean machine measured the default mode at 8.8 against 7.4, at about 5.2 times the cost ([details](docs/benchmark-modes-2026-11.md)).

**A platform-sized round (0.2.3, 2026-11-07).** Task p1 is a help-desk platform built in three stages in one session (accounts and roles, then a dashboard, then an AI feature against a fake model server), with 264 hidden tests and a 60-minute limit per stage. Each setup ran twice, at plugin commit 98338a6, and Codex judged every group blind in two orders:

| | Cost (mean, API rate) | × solo | Hidden tests (mean of 264) | Codex judge (mean) | Ranked 1st | Stages in time |
|---|---|---|---|---|---|---|
| Plain Claude Code (solo) | $4.22 | 1.0 | 264 | 7.5 | 0 of 4 | 6 of 6 |
| Lean | $9.82 | 2.3 | 264 | 7.75 | 0 of 4 | 6 of 6 |
| **Balanced (default)** | $18.79 | 4.5 | 263 | **8.75** | **4 of 4** | 6 of 6 |
| Max | $25.78 | 6.1 | 210 | 7.0 | 0 of 4 | 5 of 6 |

Balanced was ranked first in every judged group. Lean was barely ahead of solo. Max was slower and no better: one Max run timed out in stage 3. Not one mode met all of the targets set before the round (Lean at most 2× solo cost and +1.0 judged; Balanced at most 3.5× and +1.5; Max the best judged). The plan check (`plan-advisor`) never ran, because p1's first stage is a single-area API, so the foundation flow did not start. The supervisor's own chat peaked at 189K to 205K tokens in team runs, against 154K to 176K for solo. Two runs per setup, one judge model.

**A second p1 round (0.3.0, 2026-11-09).** The same task, judge and limits, at plugin commit 5b9ba51 (two modes, every job handed to a section, Max rebuilt with a 120-minute stage limit). Targets were set before the round:

| | Cost (mean, API rate) | × solo | Hidden tests (mean of 264) | Codex judge (mean) | Ranked 1st | Longest stage | Supervisor's chat peak |
|---|---|---|---|---|---|---|---|
| Plain Claude Code (solo) | $3.89 | 1.0 | 264 | 7.25 | 0 of 4 | 9 min | 150K to 167K |
| **Balanced (default)** | $15.96 | 4.1 | 261.5 | 8.25 | 2 of 4 | 23 min | 115K to 117K |
| Max | $36.19 | 9.3 | 262 | 8.5 | 2 of 4 | 55 min | 171K to 176K |

Met: Balanced's cost (at most 5× solo) and time (60 minutes a stage); Max judged 0.25 above Balanced, exactly its bar, with hidden tests at least Balanced's, inside 120 minutes; `plan-advisor` ran at stage 2 in all four team runs; Balanced's supervisor stayed under 150K. Missed: Balanced judged 1.0 above solo, not 1.5; both modes passed fewer hidden tests than solo; Max's supervisor went over 150K. Not measurable: Max's security pass, because the security section stopped at start in both Max runs (it preloaded `security-review`, which needs an `origin/HEAD` ref the benchmark repos lack). Every team-mode hidden failure came from a check the spec does not ask for: in three of the four runs the page refused a report whose counts were not numbers, so the plain-text test found an empty list, and one Balanced run refused a body whose invalid UTF-8 the spec says to replace. In both orders Codex picked the same winner for each pair: Balanced for the first, Max for the second. Commit f7787b0 lets the security section start without that ref and tells every section not to add checks the spec does not state; neither fix is measured yet. Codex judged on CLI 0.167, because the app had replaced the 0.166 binary of earlier rounds.

**A p1 confirm round (0.3.0, 2026-11-10).** The same task, judge, limits and targets, at plugin commit 29af0bb (that round's fixes, plus the saved request, the short hand-back and the resume brief):

| | Cost (mean, API rate) | × solo | Hidden tests (mean of 264) | Codex judge (mean) | Ranked 1st | Longest stage | Supervisor's chat peak |
|---|---|---|---|---|---|---|---|
| Plain Claude Code (solo) | $3.53 | 1.0 | 264 | 7.0 | 0 of 4 | 27 min | 149K to 152K |
| **Balanced (default)** | $17.45 | 4.9 | 262.5 | 8.0 | 0 of 4 | 34 min | 95K to 98K |
| Max | $37.37 | 10.6 | 261 | 8.75 | 4 of 4 | 54 min | 137K to 139K |

Met: Balanced's cost (4.9× solo, under 5×) and time; Max judged 0.75 above Balanced (bar 0.25), inside 120 minutes, and ranked first in every case in both orders; both modes' supervisors stayed under 150K; `plan-advisor` ran at stage 2 in all four team runs; the security section ran in every Max stage, and the judge flagged no security hole in Max. Missed: Balanced judged 1.0 above solo again, not 1.5; both modes passed fewer hidden tests than solo, and Max fewer than Balanced. Every team hidden failure was the same test: three runs decoded the request body with `new TextDecoder('utf-8')`, which drops a leading byte order mark, so a body the spec rejects was read as `{}`. The judge's other defects: a configured URL's user:password dropped (caused by the previous round's own fix), a model deadline enforced by a timer only, a model call restarted (Balanced) or answered from stale data (Max) when the ticket changed meanwhile, Node's own replies to an unknown Expect header and to CONNECT, and a login button re-enabled after the reply's body instead of when the request settled. Commits 27db531 and 44f5d45 fix these in the sections' rules; not measured yet.

**Method:** each round builds the same three tasks (a small library, a command-line tool and a web app) twice per setup. Hidden tests check correctness, then the solutions are anonymised and graded blind by Opus judges on correctness, code quality, tests, robustness and docs. The tasks, hidden tests, harness and scorer are in [`bench/`](bench/), and every round's raw scores and judge notes are in [`bench/data/`](bench/data/); a round runs real paid Claude sessions. Full results and every round's changes: [docs/benchmark-2026-10-24.md](docs/benchmark-2026-10-24.md) (final summary at the end).

## Requirements
- Claude Code with plugin support. The Team Board strip, `/team` and `/chats` use the Mods API (`hooks/register.tsx`).
- Access to the Claude 5 models: sections and the reviewer run on Opus 5.5, the coder helper on Sonnet 5.5, the scout helper on Haiku 5.5.
- Node.js 22.3 or later (or 20.16 or later) for the hooks and tests, because they use `process.getBuiltinModule`. CI runs the hook tests on 20.16, 22.3 and 26, and everything on Linux, macOS and Windows on 26.
- For headless runs (`claude -p`), set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`. Otherwise `claude -p` stops background subagents 10 minutes after the last turn, which cut off the testing section's final review in a probe on Claude Code 2.1.296. The mode round ran this way, with a time limit on each run.
- Recommended skills, preloaded by some sections: `frontend-design` (frontend), `tdd-workflow` (testing), `claude-api` (ai-llm, ai-engineer), `web-design-guidelines` (uiux). Sections load `security-review` only when the branch shares history with an `origin/HEAD` ref (`git merge-base HEAD origin/HEAD` succeeds), because the skill runs `git diff origin/HEAD...` as it loads. Other skills a job names are loaded only if they are installed.

## Install
In Claude Code 2.1.275 or later, one command installs it from this repo:
```
/plugin install section-team --marketplace afel6/section-team
```
On older versions, run `/plugin marketplace add afel6/section-team`, then `/plugin install section-team@section-team`.

To work on the plugin itself, clone it instead:
```bash
git clone https://github.com/afel6/section-team.git
```
- Try it once: `claude --plugin-dir <path-to-section-team>`.
- Keep it on: in `~/.claude/settings.json`, set `env.CLAUDE_CODE_PLUGIN_DIRS` to the clone's path. New sessions pick it up.
- Off: set `"section-team@inline": false` under `enabledPlugins`, or remove the env entry. Emergency: `claude --safe-mode`.

The section agents are generated: edit the roster in `scripts/gen-agents.mjs` and run `node scripts/gen-agents.mjs`. Skills you give a section with `node scripts/assign-skill.mjs <skill> <section>...` are kept in `scripts/roster-extra.json`.

## Use
- Just talk to the supervisor. Every job goes to a builder section, so the supervisor's chat stays small. In Balanced mode (the default): a small task (about 50 lines, one or two small functions) or a single-area task (up to about 600 lines) wakes the matching builder section, which writes the code, its tests and any README asked for, and runs its own reviewer gate; a feature with its own behaviour to test (a CLI, an endpoint, a module with storage or I/O) is never small. Multi-area work wakes the builder sections plus testing. 3+ builder sections (testing, docs, the security pass and advisors not counted) → it shows a plan first. Max changes these steps; see [Modes](#modes).
- Sections message each other directly by agent id and share contracts as notes in `.team/notes/`. If an id is missing or a message fails, the supervisor forwards the request with the asker's id, so the owner replies to the asker directly.
- The supervisor names up to 4 skills per job (`Skills for this job:`), picked from what is installed and fits that section and task.
- Reports: `.team/reports/<date>/` in each project. Every REPORT has a `Status:` line (`done`, `partial`, `blocked` or `ungraded`) and a `Quality:` line, the reviewer's grade (see Sections) or `n/a (no code)`. `ungraded` means the section truly could not run its reviewer gate (for example, it had no Agent tool) and says why; the supervisor then runs `section-team:reviewer` on that work with the mode's gate. Each saved file ends with a `Plugin:` line naming the plugin version and the project's mode.
- Notes: `.team/notes/` in each project, `INDEX.md` plus one file per note. Notes and reports both live under `.team/`, kept out of git via `.git/info/exclude`; to keep them in git, create `.team/keep-in-git` and delete the `.team/` line from `.git/info/exclude`.
- Long messages and hand-backs: a pasted message of 3000 characters or more is saved word for word to `.team/reports/<date>/<time>-user-request.md` inside a git repo whose `.team/` folder git ignores, so the supervisor points sections to it instead of re-typing it. Sections put long output (probe logs, spec readings, flow output) in a `-details.md` file there and keep at most 5 short lines above their REPORT; a builder hand-back that claims done with more than 1200 characters above its REPORT is refused (partial, blocked and ungraded are not; PreToolUse hook). A resumed session gets the brief again only when it changed since the session started. In the p1 confirm round the supervisor's chat peaked at 95K to 98K in Balanced and 137K to 139K in Max, down from 115K to 117K and 171K to 176K the round before.
- If a plugin hook fails, or has to skip its job (for example, its input names no project folder), you see one `section-team` line saying so, instead of silence. The exception: the context guard and the grade check allow silently when they cannot read a transcript.

## Modes
Each project runs in one of two modes. Lean, the third, was removed in 0.3.0: a project that saved it runs as Balanced, with a line at session start saying so, until you pick a mode. Balanced is the default; 0.2.3 changed it with the security wake-up, docs last and the whole-stack final review. The picker's labels show usage from the [mode round](docs/benchmark-modes-2026-11.md) of 2026-11, from the two single-area tasks up to all three tasks. "Measured" compares each mode with Claude Code with every plugin off, on a clean machine with no user instructions, over three new tasks: quality is blind Opus judge quality out of 10 (plain Claude Code: 7.37), and usage is cost over all three tasks, then on the two single-area tasks alone. Every setup passed every hidden test, and the setup with more test lines won almost every comparison, so read the quality gaps with that in mind.

| Picker label | Measured 2026-11 | What changes | Reviewer gate |
|---|---|---|---|
| Balanced · ~4.3–5.2× usage (measured 2026-11) | Quality 8.77, +1.40 over plain Claude Code (bar met, Codex confirms). Usage 5.24×, then 4.26×. | The steps under [Use](#use). | Opus reviewer. Pass: overall at least 8 and no item under 6. 2 fix rounds. |
| Max · ~7.5–9.7× usage (measured 2026-11) | Quality 9.06, +0.29 over Balanced (bar not measurable: Balanced is above the 8.60 scale ceiling; Codex does not confirm). Usage 9.66×, then 7.52×. | Balanced's flow plus proof steps. The testing section probes even small tasks. Single-area code that takes user input or touches files or the network also gets a security review. Multi-area work gets a security pass, then two final reviews by two fresh testing sections (the second is not shown the first's REPORT), and always wakes docs. Before it says done, the supervisor runs the testing section's one command that prints a PASS or FAIL line per critical flow. Every hand-back with a changed file, docs and config included, needs a reviewer grade. | Opus reviewer. Pass: overall at least 9 and no item under 7. 2 fix rounds.

- **Pick a mode:** the **Mode** picker on the team strip, or `/team mode balanced|max`. `/team mode` alone shows the current mode and the two labels; `/team` alone still opens the board. An unknown mode is refused and nothing is saved. On mobile the strip has no picker: tap its mode button to see the command.
- **When it applies:** a new session starts in the project's mode. A change mid-session applies from your next message: the supervisor is told the new mode and its rules, and the handback gate uses the new mode's pass mark at once. A change to `autoInstallSkills` applies from the next session.
- **Mode file:** the choice is saved in `.team/mode.json` at the project root (the main checkout of a git repo, so its worktrees share it; else the session's folder), for example `{"mode": "max", "autoInstallSkills": true}`. Both keys are optional. No file means Balanced. A session that starts with a broken file (bad JSON or an unknown mode; a saved `lean` is not broken, it runs as Balanced) runs Balanced, and a one-line message says what was wrong. If the file breaks mid-session, the session keeps its mode (the supervisor and the handback gate both), and each prompt shows a one-line warning until the file is fixed; a `/compact` or `/clear` while it is broken starts the session over in Balanced. `autoInstallSkills` overrides `SECTION_TEAM_AUTO_INSTALL_SKILLS` for that project. Like the rest of `.team/`, it stays out of git by default.

## Team Board
- Nothing opens by itself. A one-line team strip above the prompt shows who is awake, the team's tokens and helpers, how many sections sleep and the project's mode (the **Mode** picker); its **Board** button opens the board.
- `/team` opens the Team Board. Each awake section has a box with its live token use, how many helpers it started by model, and its reviewer grade once it is done; a section that ends `partial`, `blocked` or `ungraded` shows as a problem. Sections nobody woke are folded into one "N asleep" line.
- `/chats` opens a dashboard with one card per open chat: needs you, working or idle (a chat quiet for 30 minutes is idle; one that ended or has been quiet for a day drops off). It reads one status file per session in `~/.claude/section-team/sessions/`. A status file holds the project folder, the first line of your latest request (cut to 80 characters), the awake sections and the token and helper counts. Status files older than 7 days are deleted at session start.

## Sections
Builders: frontend, backend, database, testing, security, devops, uiux, docs, ai-llm, mobile. Advisors (read-only): ai-engineer, data-scientist, plan-advisor.
Section heads work like solo builders. Each reads `.team/notes/INDEX.md` first, plans its part, then hands independent tasks out in parallel to cheap helpers (not sections, not on the board as cards): `section-team:scout` (Haiku, read-only: reads and searches, returns file:line facts) and `section-team:coder` (Sonnet, routine code and tests from the head's spec). Both helpers can load skills with the Skill tool. Heads run helpers in the foreground (`run_in_background: false`; several in one message still run in parallel), because a head that waits on a background helper ends its turn and is made to hand back unfinished. The plugin refuses a section's Agent call that asks for the background (PreToolUse hook). Where the Agent tool has no such option (the desktop app), helpers run in the background and the head keeps working until their results are in. The head keeps design, tricky bugs and integration for itself. Advisors may use the scout but not the coder.
- **Notes:** a head writes a note in `.team/notes/` for anything other sections depend on (an API, a schema, design tokens, a file layout) and adds one line to `INDEX.md` (`<file> — <owner section> — <one-line summary> — <date>`). Only the owner edits its note; shared decisions are appended to `.team/notes/decisions.md`.
- **Skills:** each section preloads at most one core skill; every other skill loads on demand, the job's `Skills for this job:` list first. If no installed skill fits, a section searches the open directory read-only (`skills.sh/api/search`) and names a `Suggested skill:` in its REPORT; it never installs. The supervisor lists the suggestion in its summary and asks you; on yes it installs it through `section-team:add-skill` (a safety review, then the install) for that section. To let it install without asking whenever the review finds no red flag, set `env.SECTION_TEAM_AUTO_INSTALL_SKILLS` to `1` in `~/.claude/settings.json`, or `"autoInstallSkills": true` in a project's [mode file](#modes); a red flag, or an existing skill of the same name, still stops the install and you are told. When a job needs a skill nobody has, the supervisor searches skills.sh and GitHub through `section-team:add-skill`: a skill whose GitHub owner is listed in `skills/add-skill/trusted-sources.json` (`anthropics`, `vercel-labs`, `microsoft`) and whose review is clean installs without asking, with no setting needed; any other owner asks you.
- **Clean-code gate:** once the helpers' code is in, a builder sends its changed files to `section-team:reviewer` (never edits). In Balanced, the default: Opus grades, the pass is overall at least 8 out of 10 and no item under 6, and there are at most 2 fix rounds; the project's [mode](#modes) sets these numbers. On a fail the fix list goes to a coder and the reviewer grades again; if it still fails the section ends `Status: partial` with the grade. In Max, a REPORT whose Changed line names any file, docs and config included, needs a grade too. Jobs that change no code skip the gate in Balanced; a config file on the Changed line counts as code. The plugin enforces it at handback: a builder whose REPORT lists changed code but no grade, says done under the mode's pass mark, or says done while its reviewer scored an item under the mode's item minimum, cannot hand it back (PreToolUse hook on `SubagentHandback`). It must run the reviewer first, or hand back honestly as `Status: partial`, `blocked` or `ungraded`.
- **Memory:** each section keeps its memory per project, one folder per section in `.claude/agent-memory-local/` under the session's folder (in a git worktree session, the worktree's folder). At session start section-team adds `**/.claude/agent-memory-local/` to the repo's `.git/info/exclude`, even with `.team/keep-in-git`, so memory folders stay out of git in every folder of the repo. Remote sessions (`CLAUDE_CODE_REMOTE_MEMORY_DIR`) keep memory elsewhere, so advisors there cannot save memory. Before 0.2.0 one memory served every project; those notes stay in `~/.claude/agent-memory/section-team-*`, and copying one of those folders into a project's `.claude/agent-memory-local/` brings it into that project. Advisors may write only inside their own memory folder there.

Section heads skip your global `CLAUDE.md` (it can cost many thousands of tokens per agent) but read the project's own rule files (`CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.claude/rules/*.md`), and carry a short copy of the house rules.

## Platform readiness (0.2.3)
Changes aimed at long sessions and real multi-area platforms:
- **Fresh sections for new jobs.** A section that is kept alive across many jobs re-reads its whole history on every turn, which gets expensive. In 0.2.3 the supervisor is told to start a fresh Agent call for each new job; a message to a section only continues that same job (a fix list, a question, a resume). Builder heads also get a shorter tool list, and are told to keep tool output short. The cost of the shorter list is that builder heads have no project MCP servers: they use a CLI, or ask the supervisor to make the call. A limited head still gets `SubagentHandback`. Those sizes are one PC's measurement, taken on 2026-11-05 (Claude Code 2.1.318, about 40 plugins and 629 skills, a throwaway probe of copies of a real head told to reply "ok", not a benchmark). In the desktop app, where the difference is large, the default head starts at 71.8K tokens and a limited-tool helper at 24.7K; a limited section head has not been measured there. In the terminal the same head starts at 40.0K by default and 32.9K with the branch's tool list. The skill list alone is 30K characters on that PC; it depends on what you have installed, not on the plugin.
- **Context guard.** The guard refuses only a section that has finished: a message to a builder section that has finished with its context over 300,000 tokens is refused. A section or helper whose message is refused is sent to the supervisor (`main`), which starts a fresh section; the supervisor itself is told to start a fresh one pointed at the notes, its REPORT if it left one, and its changed files. A section still working takes messages at any size. If the plugin cannot read the needed files, it allows the message.
- **Grade check.** Only a builder REPORT that claims done with code is checked; `partial`, `blocked` and `ungraded` are not. Its grade is now compared with the reviewer's own grade in its transcript. A grade above the reviewer's, or a grade with no reviewer call, is refused at handback. If the result cannot be read, nothing is refused.
- **Foundation skill.** `section-team:foundation` is loaded by the supervisor before a new platform or product with two or more builder areas; other work with 3 or more builders keeps the short plan. It asks the user at most 5 questions, writes a short `.team/notes/foundation.md` (stack, data model, contracts, build order as vertical slices, test plan), waits for your OK, then builds one slice at a time with a whole-stack check after each. `.team/notes/plan.md` tracks the slices so a new chat can carry on.
- **Brief rules.** In Balanced, multi-area work touching auth, payments, uploads or secrets also wakes the security section; Max's security pass is unchanged, see [Modes](#modes). In every mode the docs section comes after the builders report, and the final review starts the app and drives the critical flows.
- **A two-stage benchmark task.** `bench/tasks/h7.md` is a two-stage task (build, then change it) with hidden tests for each stage and for stage-1 behaviour surviving. It exists to show whether the code is really better, because earlier tasks were passed by every setup.

**What is measured and what is not.** The cost figures behind these changes come from `bench/transcript-cost.mjs`, which prices a one-off replay of private local transcripts from 2026-10-24 to 2026-11-04 with the rates in that file: a rough model, not a bill. The replay itself is not in this repo; tests, commit messages and the platform-readiness plan (its Evidence table holds the main ones) quote some of its figures. The Results and Modes figures were measured before 0.2.3, and the guard, the limited heads, the grade check and the two-stage harness have only unit tests until a live check confirms them, and the foundation skill and the brief rules have not been run live. Not measured yet: any saving in real use, and any gain in code quality or in hidden-test failures. The h7 runs that could show this have not been done, so treat 0.2.3 as unproven until they are.
