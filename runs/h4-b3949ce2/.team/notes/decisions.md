# Decisions log — date, section, decision, why

- 2026-11-02 — backend — Save with a plain `writeFile` of the full JSON to the data path (no temp file + rename). Why: supervisor preference; it never creates any extra file, and a data file that is not writable makes the save fail (500, nothing changes) instead of being quietly replaced by a rename. Trade-off: a write that fails partway (for example a full disk) can leave the file damaged.
- 2026-11-02 — backend — Strict data-file reading: the file must be exactly `{"nextId","bookings"}`, every booking exactly the 6 keys with valid values (trimmed title, valid date/times, end after start, room known), ids unique, positive and below nextId, and no two bookings overlapping. Anything else gives `cannot read data file <name>`. Why: the spec rejects any content "not in the layout this server writes", so we take the stricter reading.
- 2026-11-02 — backend — Only `ENOENT` counts as "no bookings yet"; `ENOTDIR` (a path part is a file), `EISDIR`, `EACCES` and so on are fatal at startup. Why: the stricter reading of "fails in any other way".
- 2026-11-02 — backend (asked by testing) — package.json test script is `node --test test/*.test.mjs`, not `node --test test/`. Why: on Node 22.23, `node --test test/` tries to load the folder as a module and fails. Node expands the glob itself, so no shell is needed, and test/helpers/ is skipped.
- 2026-11-02 — backend — Content-Type media type: only spaces and tabs are trimmed, and only ASCII letters are case-folded. A repeated Content-Type header uses Node's choice (the first one). Why: this is the spec's literal wording.
- 2026-11-02 — frontend — A 200 reply missing a `rooms` or `bookings` array shows `Request failed.` (restored by supervisor from frontend REPORT).
- 2026-11-02 — frontend — Clicking an already-disabled Cancel button sends nothing.
- 2026-11-02 — frontend — Every fetch passes an options object, `{method:'GET'}` for GETs.
- 2026-11-02 — testing — Stricter readings tested: `Book` stays disabled until the reply body has arrived (not just the status); a 204 reply's body is never parsed; the rooms reply needs exactly status 200 (201 = error status); the `#error` <p> must be empty with no whitespace; the HTML must not contain the room names in any letter case. Why: each is the stricter of two readings of the spec text.
- 2026-11-02 — testing — The fake DOM throws and records a violation for any browser API outside the spec's list, and its click() reaches listeners even on disabled buttons, so app.js's own guards are what is tested. Why: the spec limits the APIs the script may use.
