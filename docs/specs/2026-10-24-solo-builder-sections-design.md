# section-team v3: solo-builder sections, per-job skills, clean-code gate, team strip, chat dashboard

Date: 2026-10-24. Status: implemented (see docs/plans/2026-10-24-section-team-v3-plan.md). Builds on `2026-10-12-claude-team-design.md`.

## Why

The user's words, condensed: each section member should be "like the solo builder that the default Claude Code used to have". That means it plans, builds, runs as many subagents as it wants on cheaper models, and members "communicate in the project so tokens be saved". The other asks:
- The supervisor hands each section only the skills and plugins that help it ("backend doesn't need uiux skills").
- Higher models check the structure, grade it and clean the code: "the coding outcome must always be clean".
- The Team Board "gets jammed" when two chats are open side by side; the user wants to hide and show it.
- A dashboard so several chats can be read easily.

Evidence from the 2026-10-24 benchmark (`docs/benchmark-2026-10-24.md`, round 2):
- Sections spend 95–97% of their cost on Opus. The Sonnet coder takes 3–5% and the Haiku scout is never used.
- Team mode costs 2.9× solo for about +1 judge point of quality.
- Every message between sections goes through the supervisor, which spends main-chat tokens on relaying.

## Goals
1. Sections do their own planning and hand the bulk of the work to cheap helpers. The Opus share of spend is measured and reported in benchmark round 3, overall and per agent (see Done means).
2. Sections share decisions through files in the project, not through the supervisor.
3. Each job carries only the skills that job needs. Sections start light.
4. All code a section delivers has passed a stronger-model quality grade of at least 8/10, or the section openly reports that it did not.
5. No pane opens by itself. A one-line team strip shows team status, and the full board opens only on request.
6. One dashboard shows every open chat as a card, with chats waiting for the user first.
7. Round 3 must not be worse than team-v2 on judge quality. Keep cost as low as possible, but **clean code wins over cost** (the user's decision). Never loosen the quality gate to save tokens; save tokens by moving work to cheaper helpers instead.

## Non-goals
- Changing the section heads' model. They stay on Opus 5.5 (the user's decision).
- Using Fable without the user's per-use approval.
- Dashboards across machines, claude.ai sync, or anything leaving the computer.
- Changing the report saver, the advisor guard, or the add-skill flow beyond what is listed here.

## Anti-goals (a failure even if it technically works)
- Code that passes its tests but is messy, duplicated or oversized.
- Runaway agent trees: helpers spawning helpers, or agents spawned with no real work to do.
- The supervisor still relaying contracts that could have been a note.
- Any pane taking screen space without the user asking.
- A failed quality grade hidden behind "done".

## Constraints
- Windows 11, Git Bash, Node 26, Claude Code 2.1.296. No npm dependencies. The plugin is live in every new session, so keep each commit working.
- Agent files are generated by `scripts/gen-agents.mjs`; never edit `agents/` by hand.
- Tests:
  - `npm test` (node:test);
  - `npm run test:board` (`claude plugin test .`);
  - `npm run validate`;
  - `node scripts/gen-agents.mjs --check`.
- The supervisor brief stays under 10,000 characters, with the marker line first.
- The global setup was just slimmed down (`~/.claude/_cleanup-backup-2026-10-24`). Do not bring heavy per-spawn preloads back.
- Every roster helper and skill must exist on this machine. As of today they do, including `fastapi-reviewer`, which was restored.

## Part 1: team strip (replaces the auto-opening pane)
- The Team Board pane no longer opens at `session.start` or on a section spawn.
- A one-line **team strip** shows in the chat window:
  - a team icon;
  - every section that is not asleep, as a state dot (running, waiting, done or problem) plus its name;
  - the helper count and team tokens;
  - "N asleep".
  - With nobody awake it reads "Team · idle".
- The strip has an icon that opens the full board, and `/team` keeps doing the same. The full board folds asleep sections into one "N asleep" line, so it stays short.
- Surface: a Mods band above the chat input is preferred. **Spike S1** (first task) confirms which surface exists and how a click on it can open the board; if a click isn't supported, the strip only shows `/team` as text.
- **Status-line fallback (approved by the user).** If the band does not show on a surface, the plugin sets its own status-line entry with `$.ui.status(text)`. The plugin API offers this directly (found while planning), so `~/.claude/settings.json` and the caveman status line are not touched.
- The data comes from the existing `board-model.mjs`. The strip is a second view of the same board data.

## Part 2: chat dashboard (cards)
- **Status file per session.** Every session writes `~/.claude/section-team/sessions/<session-id>.json` whenever its board data changes, at most every few seconds. It holds:
  - the project name (the repo folder name) and cwd;
  - the current request (first line, about 80 characters);
  - the state, one of `working`, `needs-you` or `idle`;
  - awake sections with their states;
  - the helper count and team tokens;
  - started-at and updated-at times.
- **States:**
  - `working` while a turn is running **or any section or helper is still running**. In interactive sessions the supervisor's turn ends right after it wakes sections, so the board's agent list counts too.
  - `needs-you` once the turn has ended and no section or helper is running, because Claude is then waiting for the user.
  - `idle` after 30 minutes with no update.
  - Session end marks the file ended. Ended files, and files older than 24 hours, are not shown and are cleaned up.
- **Dashboard.** `/chats` opens a "Chats" pane with one card per session file, in the same layout as the approved mockup.
  - Each card shows the project name, a state pill, the current request, the team line, and minutes plus tokens.
  - `needs-you` cards are highlighted and sorted first, then `working`, then `idle`.
  - The pane refreshes on the board's poll timer, only opens when asked, and closing it is fine.
- Local only, with no network. The status files hold no message bodies beyond the first line of the request.

## Part 3: sections work like solo builders
New job flow in every builder section's body (advisors unchanged except where named):
1. **Read the notes first.** Read `.team/notes/INDEX.md`, then only the notes relevant to the job (Part 4).
2. **Plan its part.** Write a short plan in its own context: tasks, files and order. Shared decisions go to notes, not the plan.
3. **Hand out the work in parallel**, one helper per independent task, as many as the job needs:
   - `section-team:coder` (Sonnet) writes code and tests from a precise brief: files, signatures and cases;
   - `section-team:scout` (Haiku) does all reading and searching across more than 2 files.

   Don't spawn a helper for something quicker to do yourself, roughly under 20 lines.
4. **Keep for the head** (Opus): design decisions, tricky bugs, integration, and the final check.
5. **Run the quality gate** (Part 6).
6. **Write notes** for anything other sections depend on (Part 4), then the REPORT.

Rules:
- Helpers stay leaves: they never spawn agents. There is no count limit; parallel batches are fine.
- Each helper brief names the one or two skills it should load (Part 5) and the house rules.
- `coder` and `scout` gain the `Skill` tool so they can load the named skill. **Spike S3** confirms that the Skill tool works inside a helper spawned by a section. If it does not, the head puts the few rules from the skill that matter for that task straight into the helper's brief, at most about 10 lines. Helpers get no preloaded skills either way.

## Part 4: notes in the project instead of supervisor relay
- Folder `.team/notes/` in the project root. `.team/` is already excluded from git by the SessionStart hook.
  - `INDEX.md` has one line per note: `<file> — <owner section> — <one-line summary> — <date>`.
  - The notes themselves are contracts, for example `api.md`, `schema.md`, `design-tokens.md` and `file-layout.md`, plus `decisions.md`, an append-only log of date, section, decision and why.
  - Notes stay short, at most about 80 lines each.
- **Ownership.** The owner section writes and updates its notes. Others read them but never edit another section's note; they ask the owner instead.
- **Questions between sections.** Every job message lists the agent ids of the sections that are awake. A section that can't find an answer in the notes sends its question straight to the other section's id with SendMessage.
  - **Spike S2** confirms that sibling-to-sibling SendMessage works by agent id. Phase 0 only tested names, and those failed.
  - If S2 fails, the current relay through `main` stays as the fallback, and the brief keeps the relay rules.
- **Supervisor brief:** stop relaying anything that belongs in a note; tell sections to read and write notes; keep waking sleeping sections and handling `Status: blocked`.

## Part 5: skills per job from the supervisor
- **Sections start light.** Each section's preloaded `skills:` list shrinks to at most one core skill: for example `tdd-workflow` for testing, and none for most. The rest become go-to mentions in the body. The builder decides the exact core skill per section, using the rule "the skill is needed on nearly every job of that section".
- **The supervisor picks skills per job.** Every job message gets a line `Skills for this job: a, b, c`.
  - At most 4 per job.
  - Chosen from the installed skills and plugins that fit that section and that task. Backend never gets UI/UX skills.
  - Advisors only get read-only skills.
- **Sections load them at the start of the job** with the Skill tool and pass the relevant one or two to each helper by name. A section may load another skill it truly needs, but prefers the given list.
- The roster's `skills` and `goto` and `roster-extra.json` (add-skill assignments) remain the supervisor's menu of good skills per section.

## Part 6: clean-code gate with a stronger model
- **New agent `section-team:reviewer`** (generated):
  - Model: Opus 5.5.
  - Tools: Read, Grep, Glob, Bash. Bash is only for running tests, linters and coverage; it never edits.
  - It is not a section, so the board counts it as a helper.
- **Rubric** (the user's standards). Each item gets a score from 1 to 10, plus an overall score:
  - structure and modularity;
  - naming and clarity;
  - duplication;
  - size limits: files 200–400 lines with 800 as a soft max, functions under 50 lines, nesting at most 4;
  - error handling and input validation;
  - tests: meaningful, and at least 80% coverage on new code;
  - security basics;
  - no debug leftovers.
- **Reviewer output:** the scores plus a fix list with `file:line` for each finding.
- **Pass rule:** overall at least 8 and no item under 6.
- **Section flow:**
  - After the helpers' code is in, the head sends its changed files to the reviewer.
  - On a fail, a coder applies the fix list and the reviewer grades again, for at most 2 fix rounds.
  - Still failing after that: the REPORT says `Status: partial` with the grade and the remaining issues. It is never "done".
- **REPORT** gains a line `Quality: <overall>/10 (reviewer, <rounds> fix rounds)`. The card and the board may show it.
- **Project-level final pass.** For a multi-section task, the testing section runs the reviewer once more over all changed files. It owns the final review, as today.
  - **Code ownership:** the section that wrote a file owns it.
  - If the final pass fails, testing sends each owning section its part of the fix list: directly by agent id if spike S2 works, otherwise through the supervisor.
  - The owner fixes with its own coders, and testing grades again. The same limit of 2 fix rounds applies; after that it is reported as `partial`.
- **The supervisor's own code.** When the supervisor builds a small task itself, it also runs the reviewer on its changed files before saying done, with the same pass rule and fix rounds. The user wants the outcome "always clean". Edits that contain no code (docs only, config values) skip the gate.
- **Review the diff, not whole files.** The reviewer grades the changed lines and their surrounding functions. That keeps the gate's cost proportional to the change.
- Why a separate reviewer rather than the head grading its own work: a fresh context that is not anchored on its own decisions.

## Decided by the user
- The team strip, with no side pane opening by itself (option A). Chat cards for the dashboard (option 1).
- Section heads stay on Opus 5.5 and hand work to cheaper helpers.
- Sections act like solo builders, with as many helpers as they need.
- Sections communicate through the project to save tokens.
- The supervisor provides the skills and plugins each section needs per job.
- Higher models check structure, grade and clean the code. The outcome must always be clean.
- When clean code and cost clash, clean code wins.
- After benchmark round 3 (2026-10-24): builder section heads move to **Sonnet 5.5**, while advisors and the reviewer stay on Opus 5.5. Cheaper models do the work and the Opus reviewer is the higher model that checks and grades it. This replaces the earlier non-goal "heads stay on Opus".
- After benchmark rounds 4–6: builder heads go **back to Opus 5.5**. Sonnet heads cost about half but were judged at solo level even with the enforced gate, and clean code wins over cost. The gate stays enforced at handback, by a PreToolUse hook on `SubagentHandback`.
- Cheaper path for medium tasks (user request, 2026-10-25): the supervisor builds single-area tasks up to about 600 lines itself and gates them with the reviewer. Sections wake for multi-area work. Round 6 showed this path at 8.1 quality for $0.89 on the medium task.
- After round 7 (same code quality at −77% cost, but thinner tests): on single-area tasks the supervisor also wakes **only the testing section** to write the tests. It still builds the code itself and gates it with the reviewer.
- After round 8 (the testing section was never woken: the medium CLI fell under the 150-line small tier): the small tier is now about 50 lines, and a feature with its own behaviour to test (a CLI, an endpoint, a module with storage or error handling) is never a small task.
- Round 9 confirmed the fixed tiers: medium 8.35 for $1.66, the same quality as sections-for-everything at 55% less cost. Kept.
- After round 9: heads ran helpers in the background, ended their turn to wait, and were forced to hand back unfinished. Heads now run helpers in the foreground and the plugin refuses a section's background Agent call. Round 10: hard 19% cheaper ($5.59), quality unchanged.
- After round 10: testing sends builders only failing fix lists; its verdict and optional nits stay in its REPORT. Round 11: hard 11% cheaper ($4.96), no turns after handback. Its lower hard score traced to spec-edge bugs nobody found, not to held-back nits. The small-task wording now says "storage or I/O"; input checks that throw do not make a function a feature.
- After round 11: testing probes every spec line (boundaries, empty and null, encoding, environment values) before grading; builders and the supervisor take the stricter reading of an ambiguous spec line. Round 12: 8.17 against team-v3 7.74 on the same panel, robustness 8.75 against 7.38, at $2.83 per task. Kept.
- After round 12 (a verified trace: builders "improved" exact spec values, notes were faithful): spec-named values are exact (never extended or normalized, no unstated rule) and testing asserts them with exact equality. Round 13: correctness 8.83 (hard 8.00), quality 8.15 against team-v3 7.82, but hard cost $7.88. Kept, because the user ranks clean code above cost.
- After round 13: the supervisor sends builders only failing items after the final review (optional findings go in its summary); heads re-grade with a new foreground reviewer call, never by SendMessage to a helper; the handback hook refuses a REPORT that claims done with a grade under 8. Round 14: 8.23 against team-v3 7.76, hard correctness 8.63 (above solo), $2.80 per task. Kept.
- After round 14: tests must catch near-miss implementations (reviewer tests item, supervisor small tasks, testing probe). Round 15: 8.52 against team-v3 7.82, tests 9.08, but $3.68 per task (hard $8.25) from extra reviewer fix rounds. Kept.
- If no band exists, the team line may be added to the status line next to the caveman badge.

## My calls (the user may change these)
- The quality bar: 8/10 overall, no item under 6, at most 2 fix rounds.
- The reviewer runs on Opus, not Fable, because Fable needs per-use approval.
- At most 4 skills per job; at most 1 preloaded core skill per section.
- Helpers never spawn agents, and there is no count limit. The rough rule: don't spawn a helper for under 20 lines.
- Each note at most about 80 lines; notes are owner-written and read-only for others.
- Dashboard states are working, needs-you (turn ended) and idle (30 minutes). It opens via `/chats`.
- The strip shows "Team · idle" when nobody is awake.

## Done means
- All the test commands listed under Constraints are green.
- The brief is under 10,000 characters.
- No pane opens by itself.
- In a fresh session, `/team`, `/chats` and the strip work.
- **Benchmark round 3** (`node bench/run.mjs --tag=v3 --conds=team`, then the same scoring, blind judging and aggregation, against solo and team-v2):
  - Judge quality at least team-v2's, within noise. Judge differences under 0.5 points count as equal (the benchmark doc's own noise rule).
  - Cost: reported against team-v2. A higher cost caused by the quality gate is acceptable. A higher cost from anything else (Opus heads doing routine work, extra agents with nothing to do) is a miss.
  - Every delivered REPORT shows a reviewer grade.
  - Opus share is **reported, not gated**: the whole-run share from `modelUsage`, plus a per-agent split (supervisor, section heads, reviewer, helpers) computed from the subagent transcripts. `bench/score.mjs` gets that split.
  - If round 3 misses on cost or quality: one tuning change plus one rerun at most, then report the result honestly either way. No open-ended paid reruns.
- `docs/benchmark-2026-10-24.md` gains a round-3 section.
